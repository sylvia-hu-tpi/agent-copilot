## 第一條：安全邊界

### 1.1 憑證絕不進入瀏覽器

`IMBRACE_API_KEY`、access token、AI 金鑰、`SESSION_SECRET`、`WEBHOOK_SECRET` **MUST** 只存於 server-side `runtimeConfig`。

**`runtimeConfig.public` 底下 MUST NOT 放置任何秘密** —— 該區內容會直接打包進瀏覽器。瀏覽器只持有 httpOnly session cookie，內含不可逆的 session id。

### 1.2 SDK 僅在 server 使用

**`server/` 以外的任何位置 MUST NOT `import '@imbrace/sdk'`**，包含 `app/` 與 `shared/`。前端一律透過 `server/api/**` 的 BFF 端點存取 iMBrace。

> 型別層的體現見 `shared/types/auth.ts`：該檔刻意不存在任何 token 欄位。

### 1.3 操作歸屬：寫入必須以發起者身分執行

| 操作 | 憑證來源 |
|---|---|
| **寫入**（JOIN／LEAVE／切換 mode／送出訊息） | **MUST** 走 HTTP 請求路徑，以發起者自己的 session token 執行 |
| **背景唯讀輪詢**（清單、訊息查詢） | 可借用某位連線中客服的憑證（`server/services/credentials.ts`），但 **MUST NOT** 用於任何寫入 |

兩者皆 **MUST NOT** 快取 client 實例 —— 每次當場建立，不存在全域單例。

> 理由：寫入若掛在被借用憑證的人身上，稽核軌跡會指向錯的人。這條約束的標的是**歸屬**，不是效能。

### 1.4 Webhook 必須驗簽

HMAC 驗簽 + 時間戳容忍（±5 分鐘）+ event id 去重，**三者缺一不可**。規格未取得前，webhook endpoint **MUST NOT** 對外開放。

### 1.5 日誌不得輸出訊息全文

對話內容含客戶個資。日誌、監控、錯誤回報一律只留 id 與雜湊，token 一律不進日誌。實作見 `server/utils/redact.ts`。

## 第二條：外部依賴的抽象邊界

### 2.1 未定規格的依賴，一律藏在 provider 介面之後

| 介面 | 隔離什麼 | 定義位置 |
|---|---|---|
| `ConversationEventSource` | JOIN／LEAVE 事件來源（本地快路徑 → webhook） | `server/sources/types.ts` |
| `MessageSource` | 訊息來源（輪詢 → webhook／WS） | `server/sources/types.ts` |
| `KnowledgeProvider` | 知識庫檢索（靜態 → iMBrace AI Agent → viki） | `ARCHITECTURE.md` §8.2 |
| `AIProvider` | 摘要／情緒／建議卡推論（iMBrace → viki） | `ARCHITECTURE.md` §8.2b |
| `StateStore` / `EventBus` | 狀態儲存與推播（記憶體 → Redis） | `server/state/types.ts` |

### 2.2 抽象邊界的正確性判準

替換某個 provider 的實作時，**只應改動組裝點**（factory／依賴注入處）。

若必須連帶改動 `SessionManager`、AI pipeline 或任何 `server/api/**` 路由，代表邊界劃錯了，**MUST** 先修正邊界再繼續。

### 2.3 `StateStore` 與 `EventBus` 的所有方法必須是 async

即使第一版是記憶體實作。

> 理由：若寫成同步的 `map.get()`，日後換 Redis 需修改數十個呼叫點；先寫成 `await store.get()`，換實作只需一天。

### 2.4 抽象只用於規格未定的依賴

已定案且不預期更換的依賴（Nuxt、Zod、Pinia 等）**MUST NOT** 另包一層 provider 介面。

> 理由：2.1 是為了「規格未定不阻塞開發」而付出的複雜度成本，不是通用的好習慣。
> 對確定不會換的東西套用它，只會讓每次追程式碼多繞一層。

## 第三條：Copilot 不得拖垮主線

### 3.1 最高原則

> **任何 AI 或知識庫故障發生時，客服 MUST 還能看對話、還能回覆。**

### 3.2 故障一律靜默降級

- AI 分析失敗 → **該區塊**顯示錯誤與重試，其他區塊照常運作
- 知識庫失敗 → 建議降級為無引用版本，並明確標示
- 即時更新中斷 → **MUST** 讓使用者知道畫面可能不是最新的，但不阻斷操作
- 事件匯流排的單一訂閱者拋例外 → **MUST NOT** 影響其他訂閱者與訊息流

**故障 MUST NOT 以全頁錯誤畫面或 modal 打斷工作。**（此限制的標的是「故障」；3.3 列舉的刻意阻斷不在此限。）

### 3.3 刻意阻斷使用者的情境是一個封閉集合

只有以下三種情況允許擋住使用者，**新增任何一種都需修憲**：

| # | 情境 | 為何值得阻斷 | 出處 |
|---|---|---|---|
| ① | **撞單偵測**（送出前發現他人已回覆客戶） | 重複回覆客戶的傷害遠大於多按一次按鈕 | 憲法 7.2、`ARCHITECTURE.md` §10.4 |
| ② | **主管強制介入鎖定** | 這是刻意的管理行為，且送出 API 本就必須拒絕 | 憲法 7.1、§10.6 |
| ③ | **Token 過期（401）需重新登入** | 無從降級；但 **MUST** 保留 `conversationId`，登入後回到原處 | §15.2 |

除此之外，任何故障都 **MUST NOT** 阻斷工作流程。

## 第四條：AI 輸出必須可驗證

### 4.1 一律使用 structured output，絕不解析自由文字

平台原生結構化輸出是否可用尚待確認（`ARCHITECTURE.md` §11.7）；在確認前靠 prompt 要求 JSON，但 4.2 的驗證、重試與降級一項都不能省。

### 4.2 所有 AI 輸出 MUST 經 Zod schema 驗證後才進入系統

### 4.3 `sopId` MUST 經白名單後驗

流程：先檢索知識庫 → 將 hits 作為上下文提供 → 要求模型只能從 hits 的 id 中選擇 → **後端再驗證一次**，不在白名單者直接丟棄該建議卡。

> 僅靠 prompt 交代不夠，必須有程式層的後驗。詳見 `ARCHITECTURE.md` §11.6①。

### 4.4 `confidence` 沒有真實依據時 MUST 為 `null`

`KnowledgeHit.score` 不存在時（目前的 iMBrace 路徑即是），`confidence` **MUST** 整體為 `null`，**MUST NOT** 用模型自評頂替或估算填充。有檢索分數時應為 `f(檢索分數, 模型自評, 上下文完整度)` 並經後端校準。

UI 依此欄位是否為 `null` 決定顯示或留空 —— 來源從 iMBrace 換成 viki 時 `confidence` 自然開始有值，介面不用改。詳見 `ARCHITECTURE.md` §8.2b、§11.6②。

> 寧可留空，也不要顯示一個沒有依據的數字。信心度一旦失準，客服很快就會學會忽略它，整個功能即告廢棄。

### 4.5 事實不得推測

**MUST NOT** 讓模型編造工單編號、時間、金額、政策內容。缺乏資料時填入 `requiresData` 欄位交由客服補上。

### 4.6 受控詞彙 MUST NOT 由模型自由生成

`category`、`resolution`、`actions_taken` 等統計用欄位必須取自設定檔（`config/categories.yaml`，尚未建立，M3），否則寫入 Data Board 後無法製作報表。

## 第五條：AI 產物寫入正式紀錄必須經人審

### 5.1 結案／交接摘要寫入 Data Board 前，MUST 經客服編輯確認

### 5.2 若確有自動寫入需求，MUST 標記 `reviewed_by = null`

使其可於事後被稽核篩出。

### 5.3 冪等

同一對話重複產生摘要 **MUST** 覆蓋而非新增。以 `conversation_id` 為唯一鍵，寫入前先 `search()` 再決定 `createItem` / `updateItem`。詳見 `ARCHITECTURE.md` §13.4。

> ⚠️ **待修憲（MAJOR，MUST 在 M3 開工前完成）—— 2026-08-28 由 `specs/003-analysis-trigger-policy` 提出。**
>
> 本條現行的「以 `conversation_id` 為唯一鍵覆蓋」與 M3 的結案流程**互相牴觸**：
> 同一個對話可以被不同人在不同時間結案多次（客戶回頭再問一次是常態），
> 以對話 id 覆蓋會讓前一次的結案紀錄消失，而那是真實發生過的事實。
>
> 修訂方向：**主鍵改為 uuid ＋ 以「草稿 id」為冪等鍵**。後者保留本條原本要防的東西
> （寫入逾時後客服重按，不該產生兩筆重複紀錄）—— 換的是唯一性的**範圍**，不是取消冪等。
>
> ⚠️ **MUST NOT 在 003 內修憲**（B.4 建議 MAJOR 變更於里程碑交界進行，M2→M3 交界正合適）；
> 003 完全不寫入 Data Board。詳見 `specs/003-analysis-trigger-policy/spec.md`「待修憲事項」。

## 第六條：資源使用

### 6.1 輪詢以 conversationId 為鍵共享訂閱

三位客服檢視同一對話 → **只輪詢一次**，結果 fan-out。**訂閱數歸零即 MUST 停止**。

多副本部署時 **MUST** 以 `StateStore.acquirePollLock()` 確保跨副本唯一。

> ⚠️ 前端離開對話時若漏呼叫 unsubscribe，該對話會被永遠輪詢下去 —— 這條的成立依賴呼叫端確實成對。

### 6.2 背景對話的 AI 分析 MUST 限定範圍並受節流

客服已 JOIN 但當下未聚焦檢視的對話（下稱**背景對話**）：

| 分析項目 | 背景對話 |
|---|---|
| 情緒分析 | **MUST** 執行 |
| 建議卡生成（含其必要的知識庫檢索） | **MUST** 執行 |
| 對話摘要 | **MUST NOT** 執行，延後至客服重新聚焦時補跑 |

背景重算 **MUST** 同時受兩道節流：同時進行背景重算的對話數 **MUST** 有上限，且觸發 debounce **MUST** 明顯長於前景對話。超過上限者只累積訊息計數，待名額釋出或客服聚焦時才處理。

**建議卡生成 MUST NOT 略過知識庫檢索** —— 每一次建議卡生成（前景或背景）都 **MUST** 實際發出一次檢索呼叫。那會讓建議卡上「未引用知識庫」的標示無法區分「知識庫確實未命中」與「系統刻意未查」，兩者的處置方式完全不同。（與 4.3 的白名單後驗互補：4.3 管的是引用不得杜撰，本條管的是不得刻意不查。）

> **檢索確實執行、但回傳 0 筆或呼叫失敗**時，**允許**以不含引用的通用建議呈現並標示「未引用知識庫」——那是誠實的降級，不是本條要禁止的行為（3.2 亦要求知識庫失敗時降級為無引用版本）。系統 **MUST** 保留「本次檢索是否真的跑過」的可稽核證據（`SuggestionBlock.knowledgeSearch.ran`），使上述兩種情形在事後可被分辨。
>
> ⚠️ **v3.0.1 澄清**：本句原文為「MUST NOT **以空的知識庫檢索結果**執行」。該措辭的字面範圍大於其理由段的立法意旨（意旨是禁止「刻意未查」），與 `specs/002-suggestion-knowledge-search` FR-004「檢索無結果時仍以通用建議呈現」直接牴觸。改以「略過檢索」為標的，規則的實質內容不變。

> 客服沒有 LEAVE，就代表客戶很可能仍在持續發言。背景完全不重算會讓客服每次切回都從頭等待
> （實測 AI 單次呼叫中位數 5.0 秒、最慢 12.2 秒 —— AI 才是成本與延遲的瓶頸，不是輪詢）。
> 成本控制改由上面兩道節流承擔，而不是靠「一律不跑」。
>
> ⚠️ **v3.0.0 修訂**：本條原文為「完整 AI 分析僅在前景聚焦的對話執行／背景對話只跑輕量情緒分類，
> 不生成建議卡、不查知識庫」。該措辭把成本控制的手段（不跑）寫成了規則本身，
> 導致真實使用情境（切走去回另一則對話）下客服體驗嚴重劣化。理由與影響範圍見附錄 C。

### 6.3 增量分析回傳 patch，不回傳全量

除了省 token，也避免摘要被整段重寫導致畫面跳動。

### 6.4 訊息拉取 MUST NOT 每輪取回整串對話

**平台不支援增量拉取** —— `since`／`after`／`since_id` 等八種寫法實測全部被忽略（`ARCHITECTURE.md` §9.3）。因此規則是：`limit=N` 只取最新 N 則（訊息由新到舊排序），再以本地 `lastMessageId` 比對算出增量。實測單一對話最多 398 則。

> 我方 BFF 對前端仍提供 `since=<messageId>` 參數（對帳與重連補齊用）—— 那一層的增量是本地算出來的，不是平台給的。

### 6.5 附件文字化結果 MUST 快取

一張圖、一份 PDF 只做一次分析，結果隨 message 永久保存。**MUST NOT** 在每次全量分析時重複送原始檔案給模型 —— 這是成本失控最快的路徑。

AI 管線的輸入一律是 `Message.text`（原文／vision 或文件分析產生的描述）。**MUST NOT** 拿 `caption` 當描述來源 —— 它是上傳時系統帶入的原始檔名，且客戶上傳時為空。

> 附件型別只有 `image`／`pdf`／`file` —— 平台不支援語音訊息，見 `ARCHITECTURE.md` §11.4。

## 第七條：協同與資料一致性

### 7.1 不得讓使用者誤判保護範圍

AgentCopilot 攔不住任何人在 iMBrace 官方介面操作。

**JOIN MUST NOT 實作為排他鎖** —— 平台不提供，我方也不加。策略是讓碰撞在造成傷害前被看見，而非防止碰撞。

**主管強制介入是唯一的真鎖，但強制力僅及於 AgentCopilot 內部**：

- 送出 API **MUST** 實際拒絕（**MUST NOT** 只在前端 disable）
- 介面 **MUST** 明示「官方介面不受此鎖限制」

> 讓主管誤以為已完全接管，比沒有鎖更危險。

### 7.2 送出前 MUST 做樂觀併發檢查

以 `lastMessageId` 為版本錨點。這是唯一真正能防止客戶收到重複回覆的機制。

**判斷條件 MUST 以 `sender.type` 為準，MUST NOT 使用 `direction`。** AI workflow 的自動回覆同樣是 outbound，以 direction 判斷會把 AI 回覆誤判為同事回覆，產生假警報。

> 假警報比沒有警報更糟 —— 客服學會忽略提示後，真正的撞單也會被一併略過。

### 7.3 JOIN 事件 MUST 去重

雙來源（本地快路徑 + webhook）會收到同一動作。以 `conversationId + operatorId` 為鍵，**10 秒**時間窗內視為同一事件。實作見 `server/utils/dedupe.ts`。

### 7.4 Webhook 上線後仍 MUST 保留對帳輪詢

每 30 秒比對本地與遠端的 `lastMessageId`，補上遺漏訊息。

> Webhook 會漏、會亂序、會重送。省略對帳的後果是「偶爾少一則訊息」—— 最難重現、最難追查的一類 bug。

### 7.5 主管強制介入 MUST 留稽核紀錄

紀錄誰、何時、對哪個對話、中斷了誰。

> 這是有勞資敏感性的操作。缺乏紀錄時任何爭議都無從釐清 —— 這是保護所有相關人員的需求，不只是技術需求。

### 7.6 身分與角色 MUST 以 iMBrace 為單一來源

順位：① 沿用 iMBrace 的角色／團隊設定；② 取不到時用設定檔白名單（`config/supervisors.yaml`，尚未建立，隨主管接管功能），並在介面明示為暫時方案。

**在 AgentCopilot 內自建帳號角色管理（順位 ③）MUST NOT 在未修憲的情況下實作。**

> 自建第二套權限系統的最大風險是**離職帳號漏關**。兩套系統必然出現同步落差，稽核軌跡分散會使問題無從追查。
> 待確實出現多角色、多權限組合需求時，依 B.1 提出修憲再評估（`ARCHITECTURE.md` §10.6）。

## 第八條：介面與無障礙

### 8.1 狀態資訊 MUST NOT 只靠顏色表達

情緒、撞單、服務模式等狀態必須同時具備**顏色 + 圖示 + 文字標籤**。

> 約 8% 男性有紅綠色覺辨識困難。「焦慮偏高」若只用紅線表示，對他們就是資訊遺失。

### 8.2 所有互動元素 MUST 可鍵盤操作

客服以打字為主，滑鼠切換成本高。「一鍵帶入」必須有鍵盤快捷鍵。

### 8.3 訊息流 MUST 能承受長列表

歷史可經 `skip` 分頁無限回補，列表長度沒有上限，因此 **MUST NOT** 一次渲染全部訊息節點。

**現行實作為虛擬滾動（`useVirtualList`）**；替換實作須先證明在數千則訊息下捲動與切換仍順暢（`ARCHITECTURE.md` §14.6）。

### 8.4 草稿絕不遺失

Composer 內容持續保存至 `localStorage`，送出失敗、撞單被攔、斷線、重新整理都 **MUST NOT** 清空。只有「確定送出成功」才清除。

### 8.5 文案 MUST 集中於 i18n

即使目前只有繁體中文。客服系統的用語需能統一調整，事後補 i18n 是最痛的重構之一。

## 第九條：渲染與部署

### 9.1 `ssr: false`，但以 `nuxt build` + `node-server` preset 部署

**MUST NOT** 使用 `nuxt generate` —— 會失去 `server/api/**`。

### 9.2 多副本部署前 MUST 先換上 Redis 實作

單副本才可使用記憶體實作。上 K8s 前，`RedisStateStore` 與 `RedisEventBus` 為必要條件。

> 否則 webhook 打到 A 副本、客服 SSE 連在 B 副本，推播直接失效。

## 附錄 B：治理

### B.1 違反憲法時的處理

若實作過程中發現某條約束確實不合理或無法達成：

1. **MUST NOT 默默繞過** —— 繞過的約束會在上線後以 bug 的形式出現
2. 在 PR 或 spec 中明確提出，說明衝突點與實際案例
3. 討論後修訂憲法（依 B.2 決定版號），並同步更新 `ARCHITECTURE.md` 對應章節
4. 依 B.3 掃過所有引用，並於附錄 C 留下版本紀錄

> 有先例可循：1.3 原文為「不建立全域 SDK 單例」，背景輪詢的實際需求證明該措辭過寬，
> v2.0.0 改為以「操作歸屬」為標的並明列唯讀借用的界線 —— 這是修憲，不是繞過。

### B.2 語意化版本

| 版號 | 何時遞增 |
|---|---|
| **MAJOR** | 移除或實質改寫既有條文、重新定義原則的標的、廢止整條 |
| **MINOR** | 新增條文，或把既有指引提升為硬性約束 |
| **PATCH** | 澄清措辭、補充範例與章節指標，**不改變任何規則的實質內容** |

### B.3 修訂憲法後的必要動作

**這是本專案最常犯、代價最高的錯誤（`CLAUDE.md` 已列為第一級警告）。** 同一個結論會散落在多份文件的不同措辭裡，改完「主要」那份時最危險。

```bash
grep -rn "<舊結論的關鍵措辭>" docs/                    # 例：改成四來源後，grep「三來源」
grep -rn "憲法 X.Y" app server shared test scripts     # 該條號的所有引用是否仍成立
grep -rn "<題號>" docs/IMBRACE_QUESTIONS.md            # 對外文件是否還在問已解決的問題
```

檢核清單：

- [ ] `ARCHITECTURE.md` §2 決策摘要與對應詳細章節
- [ ] 引用該條號的程式碼註解、測試名稱、spike 腳本
- [ ] `README.md` / `CLAUDE.md` 的文件地圖描述
- [ ] `IMBRACE_QUESTIONS.md`（**唯一會離開這個 repo 的文件**，過期內容會浪費對方時間）
- [ ] `.specify/memory/constitution.md`（依 B.4 重新同步）
- [ ] 附錄 C 版本紀錄

### B.4 與 GitHub Spec Kit 的同步

本文件是 `.specify/memory/constitution.md` 的**唯一來源**，方向單一：

```
docs/CONSTITUTION.md  ──複製──▶  .specify/memory/constitution.md
```

- **MUST NOT** 直接編輯 `.specify/memory/constitution.md` —— 改動會在下次同步時被覆蓋
- 本文件變更後 **MUST** 立即重新複製，並在該 PR 中一併提交
- 憲法變更會影響**後續所有** feature 的 plan 生成，因此 MAJOR 變更 SHOULD 在里程碑交界時進行
