## 這份規格為什麼存在

001～004 交付的是**新能力**；這一份交付的是**那些能力在真實環境跑起來之後才顯形的缺口**。
四類項目彼此的技術主題不同，但共通點只有一個而且很重要：

> **它們全部不會報錯。** 兩個雙分頁缺陷讓客服的畫面安靜地停止更新；
> 恢復不補算讓情緒走勢中間缺一段而沒有任何提示；杜撰引用被白名單擋下後
> 只是「這次沒有引用」；並行度與 `user_id` 只影響延遲數字。
> 沒有一項會讓測試變紅、讓型別報錯、或讓客服看到錯誤訊息。

`m2-004-done` 已於 2026-09-02 押下，押的是「002／003／004 的實作與文件收尾完成」，
不是「M2 全部驗收通過」。本規格是 M2 里程碑 tag（`m2-done`）之前剩下的、
**本 repo 有能力關閉**的部分。

## Clarifications

### Session 2026-09-02

- Q: 單次恢復的補算，一輪最多可以補多少？ → A: 每輪最多 3 批（＝18 則客戶發言），對齊 `SENTIMENT_CONCURRENCY` 的一波並行；剩餘缺口由後續輪次（下一次新客戶發言）繼續補
- Q: 情緒 15 秒 p90 這條門檻要怎麼處理？ → A: 維持 15 秒不動，先跑完 FR-018 的並行度掃描再決定（實測顯示放寬到 20 秒仍只有 84%，撈不到任何樣本）
- Q: 「這次為什麼沒有引用」的證據要留在哪裡、給誰看？ → A: 只留在伺服器端的具名事件（標準輸出為完整集合），前端不加欄位——`hitCount` 已能分辨「未命中 vs 未引用」，前端沒有任何處置會因「被捨棄」而不同。統計面交給 FR-017 的量測腳本，個案排查交給 FR-015 的事件。額外落點（本地檔）與集中式收集（Loki 等）屬 plan 與 M4 部署決策，spec 不指定格式
- Q: 憑證登記需不需要一個不依賴連線關閉事件的存活兜底？ → A: 需要，沿用 presence 既有的心跳＋TTL 模式（存活訊號須提升到連線層級）——沒有它，US1 的修法會讓現行「同一客服下次登記覆蓋上一筆」的意外自癒消失，每次洩漏都永久累積
- Q: FR-017／FR-018 的量測，最小樣本口徑訂多少才算數？ → A: 三輪、n=45（沿用既有歷史口徑），輪次間輪換順序，同一時段連續跑完。FR-018 是「每檔位」n=45（輪換檔位順序），FR-017 是「15 段對話 × 3 輪」（輪換對話順序）——杜撰率沒有檔位這個維度。實跑成本：FR-018 約 1 小時、FR-017 的基線與改動後各約 21 分鐘，合計約 1 小時 40 分

> 給 `/speckit-plan` 的方向（非需求，可被更好的方案取代）：額外落點若採本地檔，JSONL 比 JSON 陣列穩（寫壞只壞一行、寫入成本與檔案長度無關、aggregator 原生可讀）；PII 用型別守（在事件型別上把 `text`／`title` 標成 `never`，讓「順手記進去」編譯期就過不了）比靠 review 可靠；⚠️ **相對路徑預設值有坑** —— dev 的 cwd 可寫，容器的 WORKDIR 屬 root 卻跑非 root，且 bind mount 會遮蔽映像裡的 `chown`。

## User Scenarios & Testing *(mandatory)*

### User Story 1 — 開第二個分頁不會讓第一個分頁安靜死掉 (Priority: P1)

客服習慣同時開兩個瀏覽器分頁看同一套後台（一個盯清單、一個處理當前對話）。
處理完之後關掉其中一個，**另一個分頁從此收不到新訊息，但畫面看起來完全正常**：
訊息流還在、輸入框還能打字、送出也會成功，只是客戶接下來說的話再也不會出現。
客服要等到客戶打電話抱怨「我剛剛傳的你都沒回」時才會發現。

這條路徑上有兩處各自獨立的失效，症狀輕重不同但成因同一個家族：

- **憑證登記**：`registerCredential()` 以 `(orgId, operatorId)` 為鍵，
  取消登記時無條件把該 operator 的項目整個刪掉。關掉其中一個分頁 →
  仍開著那條的憑證一併消失 → `borrowCredential()` 回 null → 兩層輪詢拉回空陣列 →
  **那個分頁從此收不到任何新訊息**。
- **Copilot session 的觀察者清單**：`session.watchers` 是去重的 operatorId 陣列，
  移除時無條件 filter，同一客服關掉一個分頁即歸零 → `deleteCopilotSession()` 被呼叫 →
  錨點不再前推，**自己送出的訊息會被當成新訊息再 fan-out 一次**。

**Why this priority**：這是四項裡唯一會讓**主線功能**（看得到新訊息）失效的，
而且失效方式是靜默的。憲法 3.1「Copilot 是輔助，不得拖垮主線」守的正是這條線，
而這個缺陷是從主線自己這一側破的。

**這個缺陷的形狀已經自己說出了修法**：`session-manager.ts` 的同一個函式裡，
`pipeline.refs` **有** refcount 且正確（`releasePipeline()` 先 `refs--` 再判斷是否為 0），
`session.watchers` **沒有**（無條件 filter 到空就刪 session）。
**同一件事由兩個計數器回答，而它們給出不同答案** —— 這個不變式破裂本身就是 bug 的形狀，
不需要再論證哪一個是對的。`PollingMessageSource.subscribe()` 更早就記載過同一個坑
並改用每次訂閱各自唯一的鍵解決。

**Independent Test**：同一位客服帳號開兩個分頁連上同一個組織／同一段對話，
關掉其中一個，驗證另一個仍持續收到新訊息、且自己送出的訊息不被重複 fan-out。
單獨交付這一條就已經消除一類客服會回報「訊息不見了」的事故。

**Acceptance Scenarios**:

1. **Given** 同一位客服以兩條連線登記憑證，**When** 其中一條關閉，
   **Then** `borrowCredential()` 仍取得另一條的憑證，該組織的兩層輪詢不中斷。
2. **Given** 同一位客服的兩條連線都已 attach 同一段對話，**When** 其中一條關閉，
   **Then** Copilot session **不被刪除**、錨點繼續前推，客服自己送出的訊息不再被當作新訊息。
3. **Given** 同一位客服的兩條連線都已關閉，**When** 最後一條關閉完成，
   **Then** 憑證與 session 才真正被清掉，不留下用已登出 token 繼續輪詢的殘留。
4. **Given** 兩位**不同**客服各開一條連線，**When** 其中一位離開，
   **Then** 另一位不受影響（既有行為不得退步）。

### User Story 2 — 故障排除之後，情緒走勢不留永久空洞 (Priority: P2)

AI 服務故障期間，某幾批客戶發言的情緒分析失敗了。故障排除後客戶又說話，
系統自癒重新開始分析 —— **但只分析新說的那些**。
先前失敗那一段的情緒點永久缺席，除非客服離開再重新接手走一次冷啟動。

客服看到的是一條中間斷掉的情緒走勢，而畫面上沒有任何東西告訴他那段是缺的，
不是「客戶那段時間情緒平穩」。**判讀一條有缺口的走勢比判讀一條沒有走勢更危險** ——
後者他知道自己不知道。

**Why this priority**：不影響主線、也不會讓客服失聯，但它污染的是 001 的核心產出
（情緒走勢的可讀性），而且錯的方向是「看起來有資料」。

**Independent Test**：注入 AI 故障讓中段若干批失敗，排除故障後由新客戶發言觸發恢復，
驗證情緒時間軸涵蓋到全部客戶發言、沒有中斷區間。

**Acceptance Scenarios**:

1. **Given** 分析過程中有若干批情緒分析失敗，**When** 故障排除後出現新的客戶發言，
   **Then** 恢復的那一輪同時補齊先前未涵蓋的客戶發言，情緒時間軸不留缺口。
2. **Given** 未涵蓋的客戶發言數量很大（長對話累積），**When** 恢復觸發，
   **Then** 補算受明確上限節流（每輪最多 18 則缺口訊息＝3 批），不得一次對同一個 agent 開出無界的呼叫量。
3. **Given** 補算過程中又有批次失敗，**When** 該輪結束，
   **Then** 區塊維持 `error` 等待手動重試，**MUST NOT** 自行再排一輪
   （003 SC-001 的止血不得因本規格而失效）。
4. **Given** 沒有任何未涵蓋的客戶發言，**When** 新發言觸發增量，
   **Then** 行為與現況完全相同，不因補算邏輯而多出任何呼叫。

### User Story 3 — 建議卡為什麼沒有引用，答得出來 (Priority: P2)

知識庫明明有相關內容，建議卡卻標示「未引用知識庫」。
成因是建議卡 agent **杜撰了 `sopId`**，被憲法 4.3 的白名單整卡捨棄 ——
白名單擋下杜撰引用是正確行為，但結果是 004 SC-002「90% 的對話最終取得帶 SOP 來源的建議卡」
只達到 **80%**。

已知的事實：10 次帶命中的第二段生成中 2 次整批捨棄；有內部資料的 9 次中 4 次（44%）
至少含一張杜撰引用。無效 id 的形狀是**憑空造一個長得像 id 的字串**，
不是填錯欄位（填成標題）或複製時被截斷 —— 因此不是改一句話就能修掉。
而且杜撰率有明顯的**對話相依性**：某一段對話三次量測全數含杜撰、另兩段一次都沒有。

**Why this priority**：這是 004 唯一未達的功能性判準，且目前沒有人能回答
「這次為什麼沒有引用」—— 是知識庫真的沒命中、還是模型杜撰後被擋掉？
兩者的處置完全不同，而畫面上長得一模一樣。

⚠️ **本規格 MUST NOT 承諾把 SC-002 拉到 90%。** 最強的槓桿是建議卡 agent 的
system prompt 與選型，兩者都在 iMBrace 後台、不在本 repo（§11 「agent 的 system prompt
也不在版本控制裡」）。本規格能交付的是兩件 repo 內做得到的事：
① 把本次可用的 `sopId` 以**封閉清單**的形式明示在我方組出的 context 裡，
② 建立可重複的杜撰率量測與歸因。

**Independent Test**：對固定的一組真實對話重複量測，能穩定產出「杜撰率」與
「哪些對話會杜撰」兩項數字，且該數字在強化命中清單前後可比較。

**Acceptance Scenarios**:

1. **Given** 第二段生成帶著本次的知識庫命中集合，**When** 組出送給模型的 context，
   **Then** 可用的 `sopId` 以封閉清單呈現並明示只能從清單中選，不得自創。
2. **Given** 第二段回傳的卡片含不在命中集合裡的 `sopId`，**When** 白名單後驗執行，
   **Then** 行為與現況完全相同（整卡捨棄），且該次捨棄留下可稽核的證據，
   足以事後分辨「知識庫未命中」與「命中了但引用被捨棄」。
3. **Given** 一組固定的真實對話，**When** 重複執行量測，
   **Then** 產出杜撰率與逐對話的分布，可判斷杜撰是否集中在特定對話上。
4. **Given** 第二段的卡片全數被捨棄，**When** 該輪結束，
   **Then** 維持 004 定案的靜默行為 —— 不重試、不閃「重試中」、不轉 `error`。

### User Story 4 — 情緒延遲還剩的那個槓桿，量過再決定 (Priority: P3)

`docs/ARCHITECTURE.md` §18 M2「情緒 15 秒 p90」目前 35/45 ＝ 78%，未達 90%。
情緒的總時間 ≈ ⌈批次數 ÷ 並行度⌉ × 單次延遲，而**並行度是這條門檻唯一還沒用過的
repo 內槓桿**（2026-09-01 由 1 改成 3 時，中位由 16.9 秒降到 7.7 秒）。

但調高並行度的風險是靜默的：並發可能讓平台側排隊而抬高**單次**延遲，
一旦單次超過 15 秒逾時就會觸發重試、重試用盡則整批轉 `error`。
也就是「總時間變短」與「失敗率上升」可能同時發生，而畫面上只會看到偶發紅字。

同一組主題下還有一項純衛生的欠帳：AI 呼叫至今未帶 `user_id`，
每次呼叫因此多一趟往返（實測值 54ms），§8.2b 已列為「未做（衛生）」。

**Why this priority**：不修不會壞任何東西，但不量就永遠只能猜。
排在最後是因為它的產出是「一個有依據的數字」，不是一個功能。

**Independent Test**：跑一次並行度掃描，對每一個檔位同時得到總時間與單次失敗率兩列，
足以支撐「要不要改」這個決定。

**Acceptance Scenarios**:

1. **Given** 並行度掃描腳本，**When** 對 3／4／5 三個檔位各跑三輪（每檔位 n=45，
   輪次間輪換檔位順序），**Then** 每一檔位同時產出總時間分布**與**單次呼叫失敗率，兩列並陳。
2. **Given** 掃描結果顯示某檔位總時間更短**且**單次失敗率未上升，
   **When** 決定是否採用，**Then** 依該判準採用並把證據寫進正典文件。
3. **Given** 掃描結果顯示總時間變短但失敗率上升，**When** 決定是否採用，
   **Then** **MUST NOT** 採用，並把「總時間變快不足以作為理由」這個結論留在文件裡。
4. **Given** AI 呼叫改為帶上 `user_id`，**When** 既有的分析路徑執行，
   **Then** 行為完全不變，僅少一趟往返。

### Edge Cases

- ⚠️ **「主動離開」與「關掉分頁」MUST NOT 走同一條路** —— 這是本規格最容易改錯的地方。
  客服在其中一個分頁按下**「離開對話」**時，該客服**所有**分頁的面板都應該一起消失
  （`specs/003-analysis-trigger-policy` T032a 於 2026-08-28 驗過，是刻意的正確行為：
  離開是一個關於「這個人」的決定，不是關於「這個分頁」的）。
  而**關掉分頁**只是少了一條連線，其他分頁必須完全不受影響。
  把計數加上去之後，若兩者共用同一條清理路徑，就會把 T032a 已驗過的行為改壞 ——
  修好一個靜默缺陷、換來另一個。
- **同一客服同時有三條以上連線**（第三個分頁、或手機同時登入）：計數必須對到底，
  不是只處理「兩條」這個特例。
- **連線異常中斷而非正常關閉**（網路斷、瀏覽器崩潰）：清理仍須發生，
  不得因為改成計數而讓憑證永遠留著 —— 那會變成「用已登出的 token 繼續輪詢」，
  比原本的缺陷更嚴重。
  ⚠️ 這條**不能只靠「走同一條清理路徑」**（FR-005）—— 那假設了關閉事件一定會觸發。
  保證來自 FR-005a 的存活兜底。
- **同一客服的兩條連線 attach 的是不同對話**：其中一條關閉時，
  另一條對話的 session 不受影響。
- **同一客服的第二條連線 attach 同一對話時，`session.opened` 的 `reason` 由 `join` 變為 `resume`**：
  這是 FR-003 改為連線計數的**連帶行為變更**（新語意＝「這個對話在我 attach 之前已經有人在看」，
  不再區分那個人是不是自己）。目前無前端消費者，但回歸清單 MUST 點名它，
  不得因為「沒有東西會紅」而漏掉。
- **冷啟動時情緒整批失敗、時間軸為空**：見 FR-008 —— 整個抓取視窗都算缺口，
  由下一則客戶發言帶動補算；不得因為沒有左界就跳過。
- **補算與新發言同時發生**：補算進行中又來新訊息，兩者不得互相覆蓋或重複計算同一批。
- **補算期間客服 LEAVE**：003 FR-012 的「離開後不排入新分析」優先，
  補算 MUST 停止（已在飛的不中斷）。
- **知識庫本次真的 0 命中**：封閉清單為空集合時，模型只能產出無引用的通用建議，
  這是合法降級（002 FR-004），不得因為清單為空就跳過生成。
- **並行度掃描期間平台正好處於降級時段**：量測結果 MUST 標註時段，
  不得在降級時段的樣本上下永久結論（這是 2026-09-02 已經犯過一次的錯）。

## Requirements *(mandatory)*

### Functional Requirements

#### 多連線的計數（US1）

- **FR-001**: 憑證登記 MUST 以「每一次登記各自唯一」為單位，而非以客服身分為單位；
  同一位客服的多次登記 MUST 各自獨立存在。
- **FR-002**: 取消登記 MUST 只移除該次登記；只有當同一位客服的**所有**登記都取消後，
  該客服的憑證才從登記本消失。
- **FR-003**: Copilot session 的觀察者記錄 MUST 對同一位客服的多條連線計數；
  只有當該客服的**最後一條**連線離開、且無其他客服在觀察時，session 才得以刪除。
- **FR-004**: 上述兩處的計數 MUST 與同一路徑上既有的管線計數（`pipeline.refs`）
  在任何時刻給出一致的答案 —— 「同一件事只有一個真相」是本組需求的驗收核心。
- **FR-005**: 連線異常中斷 MUST 與正常關閉走同一條清理路徑，不得留下無主的登記；
  該路徑未被觸發時（關閉事件沒來），或登記已由 FR-005a 的心跳重建、不再屬於任何連線的
  關閉路徑時，MUST 由 FR-005a 的存活兜底在 TTL 內回收。兩者合起來才是「不留無主登記」的保證。
- **FR-005a**: 憑證登記 MUST 具備**不依賴連線關閉事件**的存活兜底：登記帶最後存活時間，
  逾期未更新即回收。存活訊號 MUST 是**連線層級**的（分頁開著但尚未進入任何對話時仍須送達），
  比照 presence 既有的心跳＋TTL 模式（`PRESENCE_TTL_MS` 45 秒／前端 20 秒心跳）。
  存活訊號 MUST 能在登記已被 TTL 剔除後**重建該登記**（心跳是 upsert）——
  否則兜底本身會製造新的失聯：瀏覽器對背景分頁的計時器有節流，
  心跳被壓到慢於 TTL 時登記會被剔除，而 SSE 連線並未中斷、不會有重連來重新登記。
  ⚠️ **這是 FR-001 的必要配套，不是額外的保險。** 現行以客服身分為鍵的實作有一個
  **意外的自癒**：同一位客服下次登記會覆蓋上一筆，所以就算關閉事件沒觸發，
  洩漏也最多活到他下次上線。改成「每次登記各自唯一」之後這個自癒消失，
  **每次洩漏都永久累積** —— `borrowCredential()` 永遠不回 null（該組織的兩層輪詢
  永遠不停，用著已登出的 token）、`hasForegroundOperator()` 永遠回 true（維持 3 秒快輪詢）。
  少了本條，US1 等於用一個看得見的缺陷換一個看不見的。
  ⚠️ 本段「心跳 MUST 是 upsert」的論證，**正典是 `contracts/connection-lifecycle.md` §4**；
  本條、Clarifications、`data-model.md` §1、`tasks.md` 必讀 3a 皆為摘要。改動時以該處為準，
  並 grep 其餘複本。
- **FR-006**: 不同客服之間的既有行為 MUST NOT 退步：一位客服離開不影響其他客服的
  憑證、session、presence 或分析。
- **FR-006a**: 客服**主動離開對話**時 MUST 對該客服的**所有**連線生效（面板一起消失），
  與「關掉其中一個分頁」明確分屬兩條路徑。連線關閉 MUST 只影響該條連線；
  主動離開 MUST 越過連線計數、直接對該客服整體生效。
  ⚠️ 003 T032a 已於 2026-08-28 驗證主動離開的傳播行為，本規格 MUST NOT 使其退步。

#### 恢復時的補算（US2）

- **FR-007**: 恢復分析時 MUST 以「情緒時間軸已涵蓋到哪裡」為基準判斷缺口，
  而非以「這次收到哪些新訊息」為基準。
- **FR-008**: 補算 MUST 涵蓋所有未被涵蓋的客戶發言，不限於本次故障期間失敗的批次。
  情緒時間軸**為空**時（冷啟動情緒整批失敗），沒有「已涵蓋到哪裡」可當左界，
  MUST 視整個抓取視窗的客戶發言為缺口（與重連快照路徑既有的約定一致），
  由下一則客戶發言帶動補算，不得因為沒有左界就跳過。
- **FR-009**: 單次恢復的補算量 MUST 有明確上限：**每輪最多 18 則缺口訊息**
  （＝3 批 × `SENTIMENT_CHUNK_SIZE`，對齊 `SENTIMENT_CONCURRENCY` 的一波並行，
  使補算那幾輪的延遲與現況同量級）。
  ⚠️ **操作定義是「18 則缺口訊息」，不是「3 批」**：缺口會與本輪的新客戶發言合併後才切批，
  切出來的批次數因此不可觀測；新發言本身的批次**不計入**此上限
  （單輪呼叫次數的上界是 ⌈新發言數 ÷ 6⌉ ＋ 3）。
  超過上限的部分 MUST 在後續輪次繼續補，由下一次自然觸發（新的客戶發言）帶動，
  且 MUST NOT 因此製造額外的自動重試輪次。
- **FR-010**: 補算失敗時 MUST 停在 `error` 等待手動重試，**MUST NOT** 自行再排一輪
  （003 SC-001 的止血優先於本規格的補齊目標）。
- **FR-011**: 客服已離開該對話時 MUST NOT 排入補算（003 FR-012 優先）。
- **FR-012**: 無缺口時的行為 MUST 與現況逐一相同，不得因補算邏輯而增加任何 AI 呼叫。

#### 引用品質（US3）

- **FR-013**: 送給建議卡生成的 context MUST 把本次可用的來源識別碼以**封閉清單**呈現，
  並明示只能從清單中選用、不得自創。
- **FR-014**: 白名單後驗的行為 MUST NOT 改變 —— 引用不在本次命中集合中即整卡捨棄
  （憲法 4.3），本規格只改變「送進去的東西」，不改變「擋下來的規則」。
- **FR-015**: 系統 MUST 保留足以事後分辨下列五種情形的稽核證據：
  ① 知識庫本次未命中、② 命中了但模型未引用、③ 命中了但引用被白名單捨棄、
  ④ 命中了但模型未回任何卡（含整批未通過 Zod 驗證）、⑤ 命中了但第二段呼叫失敗
  （FR-016 的靜默 `none`）。④⑤ 在畫面上與 ①②③ 一樣都是「未引用知識庫」，
  少了它們，SC-005 的「任何一次」就有兩種情形答不出來。
  該證據 MUST 同時滿足：
  - 落在**生產路徑**（不只量測腳本），可在不重跑分析的情況下取得；
  - 以**具名事件**呈現，事件名與必要欄位（本次命中數、模型回卡數、保留數、
    無效識別碼字串本身 —— 受長度收斂：超過 64 字元者改記雜湊＋原長度，
    見 `contracts/citation-audit-event.md` §1）是對外契約，構成 SC-005 的驗收形式；
  - **完整集合 MUST 出現在標準輸出**；任何額外落點只能是它的拷貝，
    MUST NOT 存在「只在別處才有」的證據；
  - 不含 PII（憲法 1.5）：只留 id 與雜湊，訊息全文與知識庫標題不入。
  ⚠️ 第三點是刻意劃的線。以級別分流讓標準輸出成為子集，短期能讓維運的畫面清爽，
  代價是日後接任何只收標準輸出的集中式平台都得改程式
  （SysTalk.Red 已踩在這個位置上，並自陳是代價）。
- **FR-015a**: 證據的額外落點若需開檔或建目錄，該操作失敗 MUST NOT 中止服務啟動
  或阻斷分析路徑；MUST 降級為僅輸出標準輸出，並在標準錯誤輸出留下一行可辨識的原因。
  ⚠️ **要防的是「開檔」不是「寫入」。** 由 SysTalk.Red 2026-09-01 的 SIT 事故反推：
  log 目錄 `mkdirSync` EACCES 發生在啟動最前段、早於任何 error handling，
  造成服務無限重啟 —— **日誌落不了地，卻賠掉了整個服務**（憲法 3.1 的反例，
  而兇手是日誌自己）。降級也 MUST NOT 全靜默：少了那一行，症狀只剩「檔案是空的」。
- **FR-016**: 第二段生成失敗或整批被捨棄時的行為 MUST 維持 004 的定案：靜默落 `none`，
  不重試、不顯示「重試中」、不轉 `error`。
- **FR-017**: MUST 提供可重複執行的量測，對固定的一組真實對話產出杜撰率
  **與逐對話的分布**（對話相依性是已知線索，MUST 從這裡查起）。
  樣本口徑 MUST 是**固定 15 段對話 × 3 輪 ＝ 45 次帶命中的生成**，
  輪次間輪換對話順序，同一時段連續跑完。
  ⚠️ 本條**不套用** FR-018a 的「每檔位」—— 杜撰率沒有「檔位」這個維度；
  兩者共用的只是「三輪、n=45、輪換順序、同一時段」這個結構。
  每段對話固定 3 個樣本，是「逐對話分布」看得出集中性的最小條件。
  ⚠️ 杜撰率口徑的**正典是本條**；SC-006 與 `contracts/citation-audit-event.md` §5 為複述，改口徑時以此為準並 grep 其餘。

#### 延遲量測與衛生（US4）

- **FR-018**: MUST 提供情緒並行度的掃描能力，對每個候選檔位同時產出
  **總時間分布**與**單次呼叫失敗率**兩列。
- **FR-018a**: 量測的最小樣本口徑 MUST 是**每檔位三輪、n=45**（沿用既有歷史數據的口徑，
  使新舊直接可比），輪次間 MUST **輪換檔位順序**（3,4,5／4,5,3／5,3,4），
  且全部在同一個時段內連續跑完。
  ⚠️ FR-017 的杜撰率量測**只共用「三輪、n=45、輪換順序、同一時段」這個結構**，
  不共用「每檔位」—— 杜撰率沒有檔位這個維度，它的口徑寫在 FR-017。
  ⚠️ **單輪不足以支撐任何檔位結論**：同一設定連續三輪量到 73% / 93% / 67%，
  單輪擺動 26 個百分點，大於檔位之間可能的真實差異。n=15 時 p90 由第 14 個值決定，
  一兩個樣本就能把它推走；n=45 由第 41 個值決定。
  ⚠️ **樣本 MUST NOT 並行取得** —— 並行度正是被量的那個變數，同時跑會抬高單次延遲、
  污染要量的東西。因此本量測沒有靠並行縮短時間的空間。
  成本參考（2026-09-02 實測）：一次 18 樣本的 invocation 實跑 6～8 分鐘，
  n=45 約 21 分鐘。FR-018 三個檔位合計約 1 小時；
  FR-017 另需**兩次** n=45（改 prompt 前的基線與改動後各一次）約 42 分鐘 ——
  本規格的量測總時數約 **1 小時 40 分**，排程時 MUST 以這個數字計。
  ⚠️ 並行度口徑的**正典是本條**；SC-007、plan 與 tasks T047 為複述，改口徑時以此為準並 grep 其餘。
- **FR-019**: 採用新檔位的判準 MUST 是「總時間改善**且**單次失敗率未上升」；
  只有總時間改善 MUST NOT 作為採用理由。
- **FR-020**: 量測結果 MUST 記錄執行時段，並在平台處於已知降級時段時明確標註，
  不得在降級樣本上下永久結論。
- **FR-020a**: 情緒 **15 秒 p90** 的驗收門檻 MUST NOT 因本規格而放寬，門檻的去留
  MUST 等 FR-018 的掃描結果出來後再議。
  ⚠️ **「放寬到 20 秒」已於 2026-09-02 由 n=45 原始樣本重算否決**：15 秒 35/45（78%）、
  18 秒 38/45、20 秒 38/45（皆 84%，仍未達 90%），要 25 秒才 42/45＝93%。
  破線樣本在 **16.4～21.2 秒之間為空**——成因是單次呼叫 15 秒逾時後重試，
  總時間直接跳到 ≈22 秒起，因此 18～20 秒在結構上撈不到任何樣本。
  這是機制造成的空洞，不是樣本不足。
  ⚠️ **同一個互動在本專案已經踩過一次**：`docs/ARCHITECTURE.md` §8.2b 記載
  「002 SC-001 的 20 秒門檻，在重試路徑上數學上不可能被滿足」——建議卡撞 15 秒逾時後
  `15 ＋ 1（退避）＋ 下一次呼叫` 必然破 20 秒。**門檻與逾時是耦合的，MUST NOT 分開調。**

- **FR-021**: AI 呼叫 MUST 帶上 **AI 服務端的用戶端識別**，以省去每次呼叫多出的一趟往返；
  該變更 MUST NOT 改變任何既有分析行為。
  ⚠️ 這個識別**與客服身分無關**，MUST NOT 填成客服的 `operatorId` ——
  填錯不會報錯，只會讓 AI 服務端的用量統計掛到錯的人身上。

### Key Entities

- **連線登記（Credential Registration）**：一條 SSE 連線在伺服器上的存在證明。
  目前以「客服身分」為鍵，需改為「每次登記各自唯一」。
  持有輪詢所需的憑證與活躍度，多條登記可屬於同一位客服。
- **Copilot session 的觀察者記錄（Watchers）**：某段對話目前有哪些連線在看。
  目前是去重的客服身分清單，需改為可對同一位客服計數。
  它決定 session 何時被刪除，而 session 決定錨點是否前推。
- **情緒涵蓋範圍（Sentiment Coverage）**：情緒時間軸已經處理到哪一則客戶發言。
  目前只在成功時前推，因此失敗批次會永久落在涵蓋範圍之外。
  補算的基準就是它與實際客戶發言之間的差集。
- **本次可用來源清單（Citable Source Set）**：一批訊息的知識庫檢索命中集合。
  它同時是送給模型的候選清單與白名單後驗的比對基準 ——
  目前只在後驗端被當成封閉集合，生成端未明示。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 同一位客服開兩條連線、關閉其中一條後，100% 的情況另一條仍持續收到新訊息，
  且該客服自己送出的訊息不被重複視為新訊息。對照現況：關閉其一即 100% 失聯。
- **SC-002**: 同一位客服的所有連線都關閉後，100% 的情況憑證與 session 皆被清除，
  不存在用已登出憑證繼續輪詢的殘留。
  「關閉」**包含異常中斷**：連線關閉事件未觸發時，存活兜底 MUST 在有限時間內
  完成回收（FR-005a），不得停留在「等下一次同帳號登記來覆蓋」。
- **SC-002a**: 客服在任一分頁主動按下「離開對話」後，100% 的情況該客服**所有**分頁的
  面板同步消失（003 T032a 的既有行為不退步）—— 與 SC-001 的「關掉分頁不影響其他分頁」
  同時成立，兩者是本組需求的一對夾擊條件。
- **SC-003**: AI 故障排除後由新發言觸發的恢復，100% 的情況情緒時間軸不留中斷區間；
  客服不需要重新接手即可看到完整的走勢。
- **SC-004**: 補算不使 003 SC-001 退步 —— AI 完全不可用且無新發言時，
  單一客服單一對話 10 分鐘內的分析嘗試仍不超過 1 輪。
- **SC-005**: 對任何一次「未引用知識庫」的建議卡，能在不重跑分析的情況下判斷成因屬於
  FR-015 的五種情形之一（未命中、未引用、引用被捨棄、模型未回卡、第二段失敗）。
  對照現況：五者無法分辨。
  驗收形式是 FR-015 的具名事件：以事件名與必要欄位即可判定，不需讀程式碼。
- **SC-006**: 建議卡的杜撰引用率可被重複量測，且量得出它是否集中在特定對話上。
  「可重複量測」的門檻是 FR-017 的口徑（15 段對話 × 3 輪 ＝ 45 次帶命中的生成）——
  單輪數字不構成本條的通過。
  ⚠️ 本條 **不承諾** 004 SC-002 的 80% 會提高 —— 最強的槓桿在 iMBrace 後台的 agent
  system prompt 與選型，不在本 repo。
- **SC-007**: 情緒並行度的每個候選檔位都有總時間與單次失敗率兩列數據，
  足以在不重跑的情況下支撐「採用或不採用」的決定。
  每檔位的兩列數據 MUST 達 FR-018a 的口徑，否則不足以支撐決定。
  ⚠️ 本規格期間 15 秒門檻維持不動（FR-020a）——「掃描還沒跑就先改驗收標準」
  是本條刻意排除的做法。
- **SC-008**: 上述所有變更後，001～004 的既有驗收全部維持通過，無退步。

## Assumptions

- **雙分頁缺陷的修法方向已由現況決定，不需另行論證**：同一份程式碼裡
  `pipeline.refs` 已經是正確的計數實作、`PollingMessageSource.subscribe()` 已經用
  「每次訂閱各自唯一的鍵」解決過同一個坑。本規格假設這兩處比照辦理，
  而不是引入第三種寫法。
- **補算的上限沿用既有的批次概念**，不新增「這個區塊分析到第幾批」的持久化狀態 ——
  那正是 `SENTIMENT_CHUNK_SIZE` 註解裡刻意迴避的第四種狀態
  （會與 003 FR-014 的 analyzing/retrying/error 三態機衝突；⚠️ 是 003 的 FR-014，
  本規格的 FR-014 是白名單規則）。
- **杜撰引用的量測沿用既有的量測腳本骨架**（`npm run spike:*`），
  不另建一套量測基礎設施。
- **並行度掃描的樣本沿用既有的真實對話組**，使結果與 2026-09-01／09-02 的歷史數據可比較。
- **判讀任何 AI 相關數字之前會先確認 agent prompt 未漂移**（`npm run spike:agent-prompts`）——
  這是 §11 的既有規則，本規格的每一次量測都適用。
- **004 定案的「第二段失敗靜默」不在本規格的修改範圍**（2026-09-02 使用者裁定）。
- 不含：平台清單預設排序的分頁邊界（外部阻塞，需對話數 > 100 的組織）、
  第一層背景輪詢的分頁（已歸屬 M4）、摘要 10 秒門檻
  （repo 內無槓桿，已裁定維持不放寬）。
