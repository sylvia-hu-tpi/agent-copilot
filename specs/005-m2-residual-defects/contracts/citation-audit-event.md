# 契約：引用稽核事件（US3）

**Spec**: [../spec.md](../spec.md)（FR-015、FR-015a、FR-017、SC-005、SC-006）
**日期**: 2026-09-02

> **這份契約就是 SC-005 的驗收形式。**
> spec 明文：「以事件名與必要欄位即可判定，不需讀程式碼。」
> 因此下表的事件名與欄位是**對外契約**，改動等同改動驗收標準。

---

## §1 事件

**事件名**：`suggestion.citation.audited`

每一次建議卡的引用結果**落定**時輸出一筆（前景兩段式的第二段落定、背景單段落定、
「命中已在手」的單段落定 —— 三條路徑都要）。
⚠️ **「落定」包含失敗**：第二段呼叫失敗、模型回 0 張卡、整批未通過 Zod，
程式上都經 `settleNone()` 把 `citation` 落成 `'none'`，那也是落定，同樣 MUST 發事件
（否則 §2 的 `no-cards`／`failed` 永遠不會出現，SC-005 對這兩種情形不成立）。

### 欄位

| 欄位 | 型別 | 說明 |
|---|---|---|
| `event` | `'suggestion.citation.audited'` | 事件名，固定值 |
| `at` | ISO 8601 | 落定時刻 |
| `conversationId` | string | 對話 id |
| `anchor` | string \| null | 這一批的錨點（`basedOnMessageId`），逐對話歸因用 |
| `stage` | `1 \| 2` | 落定來自第一段或第二段（背景單段記 `1`） |
| `hitCount` | number | **本次知識庫命中數** |
| `cardsReturned` | number | 模型回傳的卡片數（Zod 驗證後、白名單前）。呼叫失敗時記 `0` |
| `cardsKept` | number | 白名單後保留數 |
| `invalidSopIds` | string[] | **被判定為不在命中集合的識別碼字串本身**，逐筆施加下方的長度收斂 |
| `outcome` | 見 §2 | 由上列數字推導的分類 |

### 型別守（憲法 1.5）

```ts
interface CitationAuditEvent {
  ...
  /** ⚠️ 這三個欄位刻意標成 never —— 讓「順手記進去」在 typecheck 就過不了 */
  text?: never
  title?: never
  snippet?: never
}
```

⚠️ **`invalidSopIds` 不是 PII，MUST 保留。** 它是模型**憑空造出來**的識別碼字串，
不是客戶內容、不是知識庫標題，而它正是 FR-017 歸因分析的原料
（要判斷杜撰的形狀是「造一個像 id 的字串」還是「填成標題」，就得看到那個字串本身）。
沒有這一行說明，下一個讀者會以為它漏擋了而把它拿掉，SC-006 就沒有原料了。

### `invalidSopIds` 的長度收斂（憲法 1.5 的機械式保證）

```
id.length <= 64 ? id : `sha256:${sha256(id).slice(0, 16)}+${id.length}`
```

⚠️ **型別守擋不到這個欄位。** `text?: never` 那三行擋的是「有人新增欄位」，
但 `invalidSopIds` 本身是 `string[]`，內容由模型自由生成 ——
上面「它不是客戶內容」的論證是**對已觀測形狀**的歸納，不是保證。
模型哪天把整段客訴文字塞進 `sopId`，這個欄位就會把客戶內容原樣寫進標準輸出，
而型別、測試、review 全都不會響。

64 字元這個界是這樣選的：真實 `sopId` 與「像 id 的杜撰字串」都遠短於它
（兩者都是 FR-017 要看的形狀，**原樣保留**），而長段客戶內容必然超過它。
超長者改記雜湊 —— 仍能判斷「同一個超長字串是否重複出現」，但內容不外流。

⚠️ 這條 MUST NOT 被簡化成「一律雜湊」：那會讓 SC-006 失去判斷杜撰形狀的原料，
而那正是 spec US3 已經量到的線索。

## §2 `outcome` 的六值 —— SC-005 的五種成因由它分辨

| `outcome` | 條件 | 客服看到 | 成因 |
|---|---|---|---|
| `cited` | `cardsKept > 0` 且有卡帶 `sopId` | 有引用 | — |
| `no-hits` | `hitCount === 0` | 「未引用知識庫」 | ① **知識庫本次未命中** |
| `not-cited` | `hitCount > 0`、`cardsKept > 0`、但全部 `sopId === null` | 「未引用知識庫」 | ② **命中了但模型未引用** |
| `discarded` | `hitCount > 0`、`cardsReturned > 0`、`cardsKept === 0` | 「未引用知識庫」 | ③ **命中了但引用被白名單捨棄** |
| `no-cards` | `hitCount > 0`、`cardsReturned === 0`、呼叫**未**失敗 | 「未引用知識庫」 | ④ **命中了但模型未回任何卡**（含整批未通過 Zod） |
| `failed` | `hitCount > 0`、第二段呼叫失敗（重試用盡／逾時／中止） | 「未引用知識庫」 | ⑤ **命中了但第二段失敗**（FR-016 的靜默 `none`） |

⚠️ 六值 MUST 與 `settleNone()` 的每一個進入點一一對應：`hits.length === 0` → `no-hits`、
`cards.length === 0` 且未失敗 → `no-cards` 或 `discarded`（以 `cardsReturned` 分）、
`catch` → `failed`。判定順序：先 `failed`，再 `no-hits`，再依 `cardsReturned`／`cardsKept`。
`failed` 與 `no-cards` 的 `hitCount === 0` 情形一律記 `no-hits`（沒有命中就沒有引用可談）。

> **SC-005 的判準**：任何一次「未引用知識庫」的建議卡，
> 在**不重跑分析**的情況下，由這一筆事件的 `outcome` 即可判定屬於 ①～⑤ 哪一種。
> 對照現況：五者在畫面上與日誌上都長得一模一樣。
> ⚠️ 原本只列 ①②③ 三種；2026-09-02 `/speckit-analyze` 發現「模型回 0 張卡」與「第二段失敗」
> 四值都不符，而 SC-005 承諾的是「**任何**一次」，因此補為六值。

⚠️ 前端**不加任何欄位**（spec Clarifications Q3）：`hitCount` 已能分辨「未命中 vs 未引用」，
而前端沒有任何處置會因為「被捨棄」而不同。統計面交給 FR-017 的量測腳本，
個案排查交給本事件。

## §3 輸出落點（FR-015 第三點）

### 標準輸出 —— 完整集合，無例外

每一筆事件 **MUST** 以**一行 JSON**（NDJSON）寫到標準輸出。

⚠️ **MUST NOT 以 log 級別分流讓標準輸出成為子集。**
這條線是刻意劃的：級別分流短期能讓維運畫面清爽，代價是日後接任何
只收標準輸出的集中式平台（Loki 等）都得改程式 —— SysTalk.Red 已踩在這個位置上並自陳是代價。
現在劃這條線，之後接才真的零改動。

### 額外落點 —— 只能是拷貝

- 以環境變數開啟；**預設不啟用**。
- 格式 **JSONL**（一行一筆）：寫壞只壞一行、寫入成本與檔案長度無關、aggregator 原生可讀。
- **MUST NOT** 存在「只在別處才有」的證據。

⚠️ **預設值 MUST NOT 是相對路徑。** dev 的 cwd 可寫會讓這個坑在開發期完全隱形：
容器的 WORKDIR 屬 root 卻跑非 root，且 bind mount 會遮蔽映像裡的 `chown`。

### 失敗處置（FR-015a）—— 要防的是「開檔」不是「寫入」

```
try { 建目錄／開檔 }
catch { 降級為只寫標準輸出；在 stderr 留一行可辨識的原因 }
```

⚠️ 由 SysTalk.Red 2026-09-01 的 SIT 事故反推：log 目錄 `mkdirSync` EACCES 發生在
啟動最前段、早於任何 error handling，造成服務無限重啟 ——
**日誌落不了地，卻賠掉了整個服務**（憲法 3.1 的反例，而兇手是日誌自己）。

⚠️ **降級 MUST NOT 全靜默**：少了 stderr 那一行，症狀只剩「檔案是空的」，
而「沒開起來」與「沒有東西可寫」是兩件完全不同的事。

## §5 FR-017 的量測如何使用本事件

杜撰率量測（`spike:progressive` 骨架）直接收集本事件並聚合：

- **整體杜撰率** ＝ `invalidSopIds.length > 0` 的事件數 ÷ **有命中且模型有回卡**的事件數
  （`hitCount > 0` 且 `outcome ∉ { no-cards, failed }`）。
  ⚠️ 分母排除 ④⑤：模型沒回卡或呼叫失敗時談不上「有沒有杜撰」，算進分母會稀釋杜撰率
- **逐對話分布** ＝ 依 `conversationId` 分組的同一比率
  （已知線索：杜撰有明顯的對話相依性 —— 某段對話三次量測全數含杜撰、另兩段一次都沒有）
- **樣本口徑**：**固定 15 段對話 × 3 輪 ＝ 45 次帶命中的生成**，輪次間輪換對話順序，
  同一時段連續跑完。**單輪數字不構成 SC-006 的通過。**
  ⚠️ 這裡**不套用** FR-018a 的「每檔位」—— 杜撰率沒有「檔位」這個維度，
  它與 FR-018a 共用的只有「三輪、n=45、輪換順序、同一時段」這個結構。
  每段對話固定 3 個樣本，是「逐對話分布」看得出集中性的最小條件。
  ⚠️ 口徑的正典是 spec **FR-017**，本段為複述。

⚠️ 事件在**生產路徑**上發出，量測腳本跑的又是生產路徑（`runColdStart()`），
兩者天然是同一份資料 —— 這正是 FR-015「證據 MUST 落在生產路徑」換來的直接好處。

⚠️ **量測前先跑 `npm run spike:agent-prompts`**（§11）：
建議卡 agent 的 system prompt 不在本 repo，被改掉不會有 commit。
量測數字是間接證據，快照 diff 是直接證據。
