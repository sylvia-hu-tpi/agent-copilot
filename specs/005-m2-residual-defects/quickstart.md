```bash

npm test                          # vitest（單元 + 對假 gateway 的整合測試）
npm run build && npm run smoke    # ⚠️ smoke 需先 build，兩支合計約 30 秒
```

## US1 — 雙分頁（SC-001／SC-002／SC-002a）

### 自動化（`npm test`）

| 驗什麼 | 壞掉時什麼會紅 |
|---|---|
| 同一客服兩條連線，關一條 → `borrowCredential()` 仍回傳 | 憑證單元測試 |
| 同一客服兩條連線 attach 同一對話，關一條 → session 未被刪 | session-manager 測試 |
| **`watchers.length === pipeline.refs`（三組情境）** | FR-004 的等式斷言 |
| 兩位不同客服，一位離開 → 另一位不受影響 | 既有行為不退步的測試 |
| 逾期登記不被 `borrowCredential()` 回傳 | 存活兜底測試（用假時鐘推進 45 秒） |
| **漏拍 60 秒後再送一拍心跳 → 登記被重建** | upsert 測試（背景分頁節流的對策，必讀 3a） |
| **LEAVE 後該客服所有連線的面板同步消失** | SC-002a 的守衛（現況即應通過） |

⚠️ **第 1 列（關分頁不影響其他分頁）與最後一列（LEAVE 對所有分頁生效）是一對夾擊條件**，
MUST 同時存在。只驗前者時，把 LEAVE 與連線關閉合併的錯誤修法會通過測試。

### 手動（真實瀏覽器，stable 環境）

1. 同一帳號開兩個分頁 → 兩個都進同一段對話 → 關掉其中一個。
2. 從另一個帳號（或平台官方介面）對該對話送一則客戶訊息。
3. **期望**：留著的那個分頁在 4 秒內看到新訊息（§18 M1 的門檻）。
   對照現況：關閉其一即 100% 失聯。
4. 在留著的分頁送出一則訊息 → **期望**：不會閃一下重新插入（錨點有前推）。
5. 在任一分頁按「離開對話」→ **期望**：該帳號**所有**分頁的面板一起消失（SC-002a）。

⚠️ 步驟 5 要在步驟 1～4 之後做，因為它驗的正是「前面的改動沒有把 LEAVE 一起改壞」。

### 存活兜底 —— ⚠️ **這一條不能手動驗，改由自動化涵蓋**（2026-09-03 訂正）

```bash
npx vitest run test/connection-counting.test.ts    # 28 tests，假時鐘，2 秒跑完
```

**驗什麼**：45 秒無心跳被回收、每 20 秒一拍永不被回收、TTL 嚴格大於兩拍心跳（容忍漏一拍）、
漏拍 60 秒被剔除後下一拍心跳 upsert 重建。**壞掉時紅的就是這個檔案。**
對照：少了 FR-005a 時，逾期登記會**永久**留著，而且是「用已登出的 token 繼續輪詢」。

⚠️ **原本這裡寫的手動步驟（斷網後觀察）已刪除，因為它在設計上就驗不到**：

1. **要斷網的正是觀察者自己。** 斷網後你的 SSE 一起死，瀏覽器端看不到任何東西；
   想改用第二台瀏覽器觀察，那台的登記又讓該組織仍有有效憑證 —— 前提被自己破壞。
2. **這條路徑完全靜默。** `server/services/credentials.ts` 整個檔案零個 `console`；
   剔除點沒有 log，`evictExpired()` 算了 `evicted` 卻沒有任何呼叫端用那個回傳值；
   `ConversationListPoller.metrics()` 在生產程式碼從未被呼叫；`server/api/` 底下沒有任何
   debug／registry 端點（`/api/health` 是純靜態回應）。**server console 不會有輸出，不要等它。**
3. **原句「第一層輪詢停止」是錯的。** 實作是**空轉**不是停止 ——
   `fetchConversationList()` 取不到憑證就 `return []`（`server/services/copilot-runtime.ts:222`），
   迴圈照常每 30 秒跑一拍、只是不打 API。這是刻意的設計，該檔檔頭寫著
   「迴圈空轉的成本遠低於『忘記重新啟動』的風險」；`stop()` 只有 `dispose()` 會呼叫。

⚠️ **會害人誤判的陷阱：MUST NOT 用側欄對話清單判斷。** `/api/conversations` 走的是
發起者自己 session 的 token（`server/api/conversations/index.get.ts:32`），與輪詢憑證登記
**毫無關係** —— 登記全空時它照樣正常回資料。看到清單有東西不代表登記還在。

📌 **若日後要讓它變成可觀察的**（目前刻意不做，屬 005 範圍外）：最低成本的兩個位置是
`credentials.ts` 剔除點加一行 `console.warn`（計數已經算好了），或讓
`POST /api/connection/beat` 回傳 `touchCredential()` 的 `{ touched, created }`
（兩者都是純計數、不含 token，但要先確認憲法 1.1 對回應內容的界線）。

**另一半：背景分頁不能被自己的兜底殺掉**（必讀 3a）。

⚠️ **原本的寫法（切到背景十分鐘、切回來、確認仍收得到訊息）會假通過，2026-09-03 訂正。**
背景分頁的 **SSE 不會被節流**（EventSource 是 server push，瀏覽器只節流計時器），
所以它的 `session.watchers` 一直在，fan-out 照樣送得到它；被剔除的只有**憑證登記**。
而只要前景分頁的登記還在，`borrowCredential()` 就取得到 token、第一層輪詢照跑、
新訊息照樣被偵測並推給兩個分頁 —— **心跳就算寫成「找不到就 no-op」，這一步也會過。**
要讓 upsert 成為唯一能決定成敗的變數，**MUST 讓背景分頁變成該組織僅剩的登記**。

正確步驟（兩個分頁 MUST 在**同一個視窗的不同 tab**，理由見下）：

1. 分頁 A（受測）與分頁 B（對照）都進同一段對話。
2. 切到 B，讓 A 隱藏，**放置 10 分鐘以上**（等瀏覽器把 A 的計時器節流到慢於 45 秒 TTL）。
3. 切回 A，**等 20～30 秒**讓它送出一拍心跳（`CONNECTION_HEARTBEAT_MS = 20_000`）。
4. **關掉 B** —— 此時 A 的登記是該組織僅剩的一筆。
5. 從另一個帳號送一則客戶訊息。

**期望**：A 在 4 秒內看到新訊息。
對照：心跳若寫成「找不到就 no-op」，A 的登記在第 2 步就永久消失了，第 4 步之後該組織
**零筆登記** → `fetchConversationList()` 取不到憑證 → 輪詢空轉不取數 → **A 從此靜默失聯，
而畫面一切正常**（連線是綠的、橫幅不會出現，因為 SSE 本身沒斷）。

⚠️ **兩個分頁 MUST 在同一個視窗**：並排兩個視窗時 `document.visibilityState` 兩邊都是
`'visible'`，A 根本不會被節流，測試等於沒跑。
⚠️ **整個測試期間 MUST NOT 最小化瀏覽器、切到別的應用程式、或讓螢幕／機器休眠** ——
那會讓**兩個分頁一起**變成 hidden，測到的就不是這個情境。
⚠️ **前景分頁不需要靜止不動**（捲動、看訊息都無所謂），但 MUST NOT 做這三件事：
按「離開對話」（LEAVE 會影響該客服**所有**連線）、登出、切走到別的對話。

## US2 — 恢復後補算（SC-003／SC-004）

### 自動化（`npm test`，對假 AI provider）

| 驗什麼 | 壞掉時什麼會紅 |
|---|---|
| 中段若干批失敗 → 新發言觸發 → 時間軸無中斷區間 | 補算整合測試 |
| 未涵蓋量很大時，單輪 ≤ 18 則缺口訊息（新發言的批次不計入） | 上限測試（斷言 AI 呼叫次數 ≤ ⌈新發言數 ÷ 6⌉ ＋ 3，有／無新發言各一組） |
| **冷啟動情緒整批失敗、timeline 為空** → 以 `null` 錨點撈整批、整個視窗算缺口 | 空 timeline 測試（「沒有 `timeline[0]` 就跳過」的寫法會紅） |
| 補算失敗 → 停在 `error`，**MUST NOT** 自行再排一輪 | 003 SC-001 不退步測試 |
| **無缺口時，AI 呼叫次數與取歷史次數皆與現況逐一相同** | FR-012 的零成本測試 |
| **缺口的左界是 `timeline[0]`，不回頭補冷啟動視窗之前的訊息** | 左界測試（見下） |
| **缺口造在中段時補得到**（錨點是 `timeline[0]` 不是高水位） | 主線情境測試（見下） |
| 客服已 LEAVE → 不排入補算（**新寫**，不是既有測試） | FR-011 的補算路徑測試 |
| 補算與新發言同時發生 → 同一則只送 AI 一次 | 併發測試 |

⚠️ **中段缺口那一條，缺口 MUST 造在中段且其後另有成功批次**——
把缺口造在尾端時，錯用 `lastCoveredMessageId()`（高水位）當抓取錨點的實作也會通過測試，
而那個實作在真實的中段缺口上**一則都補不到**。

⚠️ **左界那一條是本組最容易漏的測試。** 造一段長度超過 `DEFAULT_MESSAGE_LIMIT`（50）的對話，
冷啟動只涵蓋最近 50 則，然後製造一次失敗與一次恢復。
**期望**：補算只補「時間軸起點之後」的缺口，**不**回頭處理前面那幾百則。
漏了它的症狀是每一次新客戶發言都額外多打 3 批 AI 呼叫，直到對話結束 ——
測試全綠、畫面正常，只有帳單會知道。

### 手動（stable 環境）

需要能注入 AI 故障。若無法注入，退而求其次：
在真實對話上觀察一次自然失敗後的恢復，確認情緒折線沒有缺口區間。

## US3 — 引用品質（SC-005／SC-006）

### SC-005：五種成因分辨得出來

**驗收形式是事件，不是程式碼**（見 [contracts/citation-audit-event.md](./contracts/citation-audit-event.md)）：

```bash
# 跑一次分析，從標準輸出撈事件
npm run spike:progressive -- "某段真實對話標題" 2>/dev/null | grep suggestion.citation.audited
```

**期望**：每一次落定都有一筆 `suggestion.citation.audited`，
且 `outcome` 落在 `cited` / `no-hits` / `not-cited` / `discarded` / `no-cards` / `failed` 六值之一
（第二段失敗與模型回 0 張卡也是落定，MUST 有事件）。
對任何一次「未引用知識庫」的卡片，由 `outcome` 即可判定成因，**不需重跑分析、不需讀程式碼**。

**額外落點的降級驗證**（FR-015a）：把落點指向一個**不可寫**的路徑並啟動服務。
**期望**：服務正常啟動、分析路徑不受阻斷、標準輸出的事件完整、stderr 有一行可辨識的原因。
⚠️ 這一條驗的是「開檔」失敗，不是「寫入」失敗 —— 要在**啟動前**就讓路徑不可寫。

### SC-006：杜撰率可重複量測

```bash
npm run spike:agent-prompts          # ⚠️ 先確認 prompt 未漂移
npm run spike:citation-quality -- <對話標題...>   # 15 段對話 × 3 輪 ＝ n=45（FR-017）
```

**期望**：產出整體杜撰率**與逐對話分布**，且改動封閉清單前後可比較。

⚠️ **本項不承諾 004 SC-002 的 80% 會提高**（spec 明文）。
最強的槓桿是建議卡 agent 的 system prompt 與選型，兩者都在 iMBrace 後台、不在本 repo。
量出來沒有改善**不代表本規格失敗** —— 交付物是「答得出為什麼」與「量得出來」。

## US4 — 並行度掃描與衛生（SC-007）

```bash
npm run spike:sentiment-concurrency        # 3／4／5 各三輪、每檔位 n=45、輪換檔位順序（約 1 小時）
```

**期望**：每一檔位同時產出**總時間分布**與**單次呼叫失敗率**兩列。

### 判準（FR-019，不得只看一列）

| 掃描結果 | 決定 |
|---|---|
| 總時間更短 **且** 單次失敗率未上升 | 採用，並把證據寫進正典文件 |
| 總時間更短 **但** 失敗率上升 | **MUST NOT 採用**，並把「總時間變快不足以作為理由」寫進文件 |

⚠️ **量測期間平台若處於已知降級時段，結果 MUST 標註時段**，
不得在降級樣本上下永久結論（2026-09-02 已經犯過一次）。

⚠️ **樣本 MUST NOT 並行取得** —— 並行度正是被量的變數。本項實跑約 1 小時，沒有壓縮空間；
加上 US3 的兩次杜撰率量測（各約 21 分鐘），本規格的量測總時數約 **1 小時 40 分**。

⚠️ **15 秒 p90 門檻在本規格期間維持不動**（FR-020a）。
「掃描還沒跑就先改驗收標準」是被明文排除的做法。

## 全域不退步（SC-008）

```bash
npm run typecheck && npm test && npm run build && npm run smoke
```

⚠️ `smoke:realtime` 會量**實際延遲**並斷言 ≤ 4 秒。機器負載重時它可能浮動 ——
**但失敗是真的訊號**，不要因為「偶爾紅」就放寬門檻，那個數字是驗收標準本身。

001～004 的既有驗收全部維持通過，特別是：

- 003 SC-001（AI 不可用時 10 分鐘內不超過 1 輪）—— 補算最容易踩爆的一條
- 003 T032a（主動離開對所有分頁生效）—— US1 最容易改壞的一條
- 004 的靜默行為（第二段失敗不重試、不閃重試中、不轉 error）
- ⚠️ `session.opened` 的 `reason`（`isResume` 語意變更，data-model §2）—— 這一項在 spec
  沒有對應的 FR／SC，只記在 data-model，因此**最容易在回歸時被漏掉**。
  現況無前端消費者，回歸時 MUST 重新確認這件事仍成立
