# Quickstart：分析管線的觸發與失敗政策

**Feature**: `specs/003-analysis-trigger-policy` ｜ **Date**: 2026-08-28

> 本規格修的是**「不該發生的事」不再發生**，因此驗證方式與前兩份規格相反：
> 多數場景不是「看某個東西出現」，而是**靜置一段時間並統計沒有東西出現**。
> 這也是為什麼 003 的驗收比 001／002 花時間 —— SC-001 本身就要靜置 10 分鐘。
>
> ⚠️ **自動化全綠不等於缺陷已修好。** 2026-08-27 的教訓正是如此：測試驗的是解析邏輯正確，
> 不是「系統真的停下來了」。US1 與 US2 的第一次驗收 **MUST** 有人用真的介面看過一眼。

---

## 前置

```bash
npm run typecheck && npm test        # 提交前的最低標準
npm run build && npm run smoke       # 動到 server/api/**、server/sources/** 時一併跑
```

⚠️ `IMBRACE_ENV=stable` 是**正式環境**。本規格的 US2／US4 驗證會實際按下 JOIN 與 LEAVE，
那是對真實客戶對話的寫入。**先挑一個內部測試對話，並讓相關同事知情。**

### 故障注入（US1、US3 必需）

US1 與 US3 都要求「AI 服務必然失敗」。三種做法，由輕到重：

| 方式 | 怎麼做 | 適用 |
|---|---|---|
| **假 gateway**（推薦，可自動化） | 沿用 `test/mock-gateway.ts`，讓 AI 端點一律回 500 | vitest 整合測試、CI |
| **不存在的 agent id** | `.env.local` 把三個 `IMBRACE_*_AGENT_ID` 改成格式合法但不存在的 UUID | 本機手動驗證，最省事 |
| 本機反向代理 | 見下方「需要在執行期切換故障時」 | **US3／T037 唯一可行的方式** |
| ~~斷網~~ | ❌ **不可行** | AI 與訊息輪詢共用同一個 gateway host（只有路徑前綴不同：`/ai-agent/**` vs `/channel-service/**`），網路層擋不掉單一路徑，擋了會連客戶訊息都收不到 |

> ⚠️ **2026-08-28 實測訂正，三點都會讓人白做工：**
>
> ① **不能「清空」agent id** —— `server/services/ai/index.ts` 在任一 agent id 為空時會退回
>    `MockAIProvider`，那是**成功回假資料**，不是失敗。必須換成「格式合法但不存在」的值。
>
> ② **平台對不存在的 agent id 回 500，不是 404** —— 因此 `classifyFailure()` 判為
>    `transient`，會走完整重試預算，畫面上**會**出現「重試中 (2/2)」。
>    （原本此處推測會是 `permanent`／不重試，實測推翻。）
>
> ③ **`.env.local` 的變更必須重啟 server 才生效**，而重啟會清空 `MemoryStateStore` 的分析
>    狀態 —— 接著只有 `join.post.ts` 會呼叫 `runColdStart()`，所以你必須 LEAVE 再 JOIN
>    才會重新分析。**這對 US3 是致命的**：那個 JOIN 本身就是手動操作，直接違反
>    「零手動操作」的判準。US3 因此必須用下面的代理方式。

### 需要在執行期切換故障時（US3／T037 必需）

`IMBRACE_BASE_URL` 指向一個本機反向代理，代理預設原樣轉發，但依一個旗標檔決定是否對
`/ai-agent/**` 回 500。設定時重啟一次，**之後切換故障不必重啟，分析狀態完整保留**。

2026-08-28 實作於 session scratchpad（`fault-proxy.mjs`，約 60 行、用完即棄，未進 repo）。
要點：只攔 `/ai-agent/` 前綴、回 500（而非 404，才能落在 `transient` 分支）、
⚠️ **憲法 1.5：絕不記錄任何 request/response body 或 Authorization 標頭** ——
那條線上跑的是正式環境的真實客戶對話。

⚠️ 代理也順帶暴露了一件事：每次 AI 呼叫實際上是**兩個** HTTP 請求
（`POST /ai-agent/chat-client/auth/user` 再 `POST /ai-agent/v2/chat`），見
`docs/ARCHITECTURE.md` §8.2 的說明。

⚠️ **MUST NOT 用「等平台真的掛掉」當驗證方式** —— 那是不可重現的，而且我們正是為了不要再對
掛掉的平台加壓才做這份規格。

## US1：AI 中斷時停止無止境重跑（P1）

### US1-A｜靜置 10 分鐘，統計分析嘗試次數（SC-001，主驗收）

```bash
# 1. 注入故障，啟動
npm run dev

# 2. 登入 → 挑一個有客戶發言的內部測試對話 → JOIN
# 3. 等三個區塊都跑完既有重試預算（畫面顯示「重試中 (2/2)」後轉為錯誤狀態）
# 4. 記下此刻的時間，然後什麼都不要做，靜置 10 分鐘
#    ⚠️ 分頁要保持開著 —— 心跳必須持續送出，那正是本場景要驗的東西
# 5. 統計期間終端機出現的 [copilot-analysis] ... 分析失敗 行數
```

| 判準 | 預期 |
|---|---|
| 10 分鐘內的分析嘗試 | **不超過 1 輪**（每區塊至多一次，含既有重試預算） |
| 對照現況（修正前） | 約 30 輪、逾 600 次呼叫 |
| 三個區塊的畫面狀態 | 各自顯示錯誤與**可按的**重試按鈕（憲法 3.2） |
| **MUST NOT 出現** | 「重試中」在錯誤狀態之後又跳回來 |

> ✅ **2026-08-28 已通過**（真實環境，`IMBRACE_ENV=stable`）：注入不存在的 agent id 後
> 三個區塊各失敗一次，靜置 10 分鐘、每 30 秒取樣共 21 點，分析嘗試**新增 0 次**；
> 期間開著兩個分頁，約 60 次 presence 心跳全部沒有觸發任何分析。
> 另有一次非注入的對照組：平台自然逾時期間同樣靜置 10 分鐘、同樣 0 次。
>
> ⚠️ **統計時要排除「手動重試的尾巴」。** 每個區塊的重試預算是 15 秒逾時 ×2 次 ＋
> 1s→4s 退避，約 40 秒才會寫出失敗行 —— 靜置開始前按下的重試，其失敗行會落在窗口的
> 前 40 秒內。判讀方式：手動重試的尾巴集中在開頭，自動重跑會跟著 20 秒心跳週期出現，
> 兩者的分布形狀完全不同。**取基準前先確認畫面已靜止，或改用每 20～30 秒取樣一次的
> 序列而非只比頭尾兩個數字。**（2026-08-28 曾因此差點誤判，重取基準才得到乾淨結果。）

### US1-B｜心跳不觸發分析（AC#3）

分析**成功**的對話（不注入故障），JOIN 後靜置 2 分鐘（至少 6 次心跳）。
終端機 **MUST NOT** 出現任何新的分析日誌，畫面 **MUST NOT** 閃過「分析中」。

⚠️ 這一項最容易被誤判為通過 —— 分析很快時畫面只閃一下。**看終端機的日誌，不要只看畫面。**

### US1-C｜手動重試後仍不進入自動重跑（AC#4）

故障狀態下按一次某區塊的重試 → 它會再失敗一次 → **MUST 停在錯誤狀態**，
不得因為「剛剛試過」就進入週期性重跑。

### US1-D｜同區塊不並行（AC#5、FR-009）

連按同一個區塊的重試鈕三次（或在兩個分頁各按一次）。
終端機 **MUST NOT** 出現三份同時進行的該區塊分析；後到的觸發合併為「跑完後再執行一次」。

## US2：LEAVE 後分析停止、面板隱藏（P1）

### US2-A｜LEAVE 後 5 秒內停止（SC-002、AC#1、AC#2）

```
JOIN 一個有客戶發言的對話 → 等分析完成 → 按下「離開對話」
→ 記時，並請另一個人（或用假 gateway）讓客戶端送出一則新訊息
```

| 判準 | 預期 |
|---|---|
| 按下離開後 5 秒內 | 不再產生任何新的分析 |
| LEAVE 後客戶送出新訊息 | **MUST NOT** 觸發分析（前提：我方系統內已無其他人 JOIN） |
| 已排入等待中的 debounce | **MUST** 被清除 |

### US2-B｜面板整欄消失，中欄完全不受影響（AC#3，本規格最容易做錯的一項）

按下離開之後，逐項確認：

| 應消失 | 應保留且持續更新 |
|---|---|
| 右側 Copilot 面板整欄 | 中欄訊息流（新訊息仍會進來） |
| COPILOT 標題列與收合按鈕 | 服務模式分段控制項 |
| —— | presence 列（同事仍會出現） |
| —— | 「載入較早的訊息」 |
| —— | **Composer 裡的草稿**（憲法 8.4，離開不等於清空草稿） |

⚠️ **MUST NOT** 是變灰、空狀態或骨架 —— 那些仍然佔位，且骨架會讓客服以為在載入而空等。
**中欄 MUST 延伸至視窗右緣**（對照畫布 artboard 1c 的「未接手」狀態）。

### US2-C｜同事仍 JOIN 時分析照常，但我這邊仍然沒有面板（AC#4）

需要兩個瀏覽器（比照 `npm run smoke:realtime` 的兩位客服設定）。

```
A、B 都 JOIN 同一對話 → A 按下離開 → 客戶送出新訊息
```

| 對象 | 預期 |
|---|---|
| B 的畫面 | 面板照常更新（分析是對話層級的，FR-014） |
| A 的畫面 | **沒有面板**，也**收不到**那些分析事件 |
| 伺服器 | 分析只跑一次（不是每人一次） |

⚠️ **A 那邊「收不到」要用開發者工具的 Network → EventStream 確認**，
不能只看畫面 —— 只在前端隱藏而伺服器照推，畫面上看起來一模一樣（FR-016a 的驗證重點）。

### US2-D｜重新 JOIN 恢復（AC#5）

A 重新 JOIN → 面板自動展開、恢復即時更新，且**先前累積的失敗批次記憶不阻擋這次分析**
（故障已排除的話應該直接跑出結果）。

### US2-E｜收合不等於離開（AC#6、FR-017a、FR-017b）

```
JOIN → 按下收合按鈕 → 面板變窄直條（對照畫布 artboard 1c 的「Copilot 面板收合」狀態）
→ 客戶送出新訊息 → 展開面板
```

| 判準 | 預期 |
|---|---|
| 收合期間 | 分析**照常執行**（展開後看得到新內容） |
| 切到另一個對話再切回來 | 收合狀態**跟著這個對話**，不是全域的 |
| 重新整理瀏覽器 | 收合狀態仍在（`localStorage`） |
| 未 JOIN 時 | 收合按鈕**不存在**（連同整欄面板一起消失） |

## US3：客戶再次發言時自動恢復（P2）

```
注入故障 → JOIN → 三個區塊都進入錯誤狀態
→ 解除故障 → 讓客戶送出一則新訊息 → 不做任何手動操作
```

| 判準 | 預期 |
|---|---|
| AC#1（服務已恢復） | 系統**自動**重新分析，面板回到正常內容（SC-003） |
| AC#2（服務**尚未**恢復） | 最多再嘗試一輪後回到錯誤狀態，**MUST NOT** 回到週期性重跑 |

⚠️ 這是「不做自動退避重試」（FR-010）能夠成立的**唯一前提**。
這一項若不通過，US1 的止血就會變成「故障後面板永遠是紅的」，整個失敗政策的取捨不成立。

> ✅ **2026-08-28 已通過**（真實環境，故障以本機代理在執行期解除，未重啟 server）：
>
> - **AC#1**：解除故障後客戶發言，**40 秒內三個區塊自動重新分析、三次 AI 呼叫全部 200**，
>   全程零手動操作；且恢復後 200 秒完全沒有再觸發（沒有退化成週期性重跑）。
>   第二則客戶訊息再次自動觸發，證明不是一次性巧合。
> - **AC#2**（故障未解除時）：客戶發言放行了失敗批次，三個區塊各重試**恰好一次**後
>   回到錯誤狀態，其後 160 秒（約 8 個心跳週期）零新增。
>
> 這一輪同時驗到失敗批次記憶的**完整循環**：擋住（反覆 LEAVE／JOIN 不重跑）→
> 被新客戶發言放行（重試一輪）→ **再次記上**（不再重跑）。第三步最容易漏 ——
> 放行後若沒有重新記錄失敗，客戶連續發言時就等同週期性重跑。
>
> ⚠️ **恢復後只補算新訊息，不補算先前失敗的那批**（實測：timeline 只剩 1 個點，
> 且因 `SentimentGauge` 的繪圖門檻而呈現為無說明的空白框）。已登記於
> `docs/ARCHITECTURE.md` M2 驗收的未完成工項。

## US4：一次重試所有失敗的區塊（P3）

| 場景 | 預期 |
|---|---|
| 三個區塊都錯誤 → 按「全部重試」 | 三個都開始重新分析（SC-004，1 次操作取代 3 次） |
| 只有部分錯誤 → 按「全部重試」 | **只有**錯誤的區塊重跑，已成功的 **MUST NOT** 被重跑 |
| 沒有任何區塊錯誤 | 「全部重試」為**不可按**狀態 |
| 按下後立刻再按各區塊的重試鈕 | 由 FR-009 的併發去重吸收，**MUST NOT** 跑兩份 |

⚠️ 按下「全部重試」到狀態回推之間有一段短暫空窗，按鈕**刻意不做樂觀 disable**
（spec.md Clarifications 定案）。那段空窗內按鈕仍可按 —— **這是預期行為，不是缺陷。**

## 回歸驗收（SC-005，不可省略）

本規格動的是 `watch()` 與 `runIncremental()` 兩個總入口，回歸風險大於功能本身。

```bash
npm run typecheck && npm test
npm run build && npm run smoke        # smoke:flow + smoke:realtime
```

| 既有驗收 | 為何可能被本規格弄壞 |
|---|---|
| 001 FR-010 重連快照 2 秒門檻 | 決策 1 改了 `watch()` —— 首次 attach 若被誤判為「無變化」，快照就不會送 |
| 002 US4 AC#5 切回前景補跑摘要 | 同上 —— 優先度升級若被誤判為心跳，摘要永遠不補跑 |
| 002 FR-019～FR-021 背景分析與節流 | 決策 3 的新門檻若寫成「前景才跑」，背景對話會整組停擺（憲法 6.2 違反） |
| `smoke:realtime` 的 4 秒門檻 | 訊息推播不該受影響；若受影響，代表 `forward()` 的過濾範圍寫太寬 |
| 憲法 8.4 草稿不遺失 | 面板隱藏若連帶重建了頁面元件，Composer 草稿可能被清掉 |

⚠️ **兩份既有測試直接測本規格改動的純函式，是最可能撞到的地方**：
`test/stream-reconnect-background.test.ts`（重連復原）與 `test/presence-away-joined.test.ts`
（away+joined 不 unwatch）。改動前先讀它們驗的是什麼 —— 若某份測試的斷言是
「每次 watch 都重新 attach」，那份斷言本身就是缺陷的一部分，應連同修正並在 commit 說明理由。

## 已知限制（預期行為，驗收時不要當成缺陷）

| 現象 | 為什麼 |

| 同事從 iMBrace **官方介面** JOIN 時，我方偵測不到，分析仍會停止 | 平台回傳的 `users[]` 是團隊名冊而非對話參與者（§10.2）。待 M4 webhook |
