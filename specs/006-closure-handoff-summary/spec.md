**Feature Branch**: `feat/m3-closure-summary`（spec 目錄 `specs/006-closure-handoff-summary`）

**Created**: 2026-09-03

**Status**: Draft

## 為什麼是現在（背景）

客服在對話中有兩個出口，**介面上的文案已經對客服承諾了行為，而行為尚未實作**：

> `conversation.exitHint`（`i18n/locales/zh-TW.json`）：「離開＝僅退出不寫入 · 結案＝產生摘要供確認後寫入」

M2 交付的「結案」目前只等同「離開 ＋ 停止分析 ＋ 隱藏面板」
（`app/composables/useConversationView.ts` 的 `closeConversation()`，M3 銜接註解在該處）。
2026-08-28 的使用者決策是**文案先行、M3 補上行為**，因此這不是缺陷而是**已知落差**；
本規格就是來關掉這個落差的，落地後 MUST 回頭確認文案與實際行為已一致。

連帶要重新處理的是 `specs/003-analysis-trigger-policy` 的 **SC-007**（找未參與者驗證兩個出口
的文案可讀性）—— 它當時因為這個落差被**決定結案**而非驗證通過。

## Clarifications

### Session 2026-09-03

- Q: 客服按下寫入後逾時（結果未知），接著又修改了草稿內容再重試，正式紀錄應以哪一版內容為準？ → A: 以草稿 id 綁定同一筆紀錄，重試時「查無則建立、查有則更新」為當下草稿內容（upsert）；紀錄內容永遠等於客服最後確認的版本。
- Q: 人審面板上，哪些欄位允許客服編輯、哪些必須唯讀？ → A: 系統計算與稽核欄位唯讀（涵蓋區間與則數、三個情緒數值、審核者／審核時間、參與客服、joinedAt／closedAt）；其餘內容欄位（摘要、意圖、分類、處理結果、實際採取的行動、情緒結果標籤、引用 SOP、後續動作）可編輯，受控詞彙欄位限白名單選擇、不得自由輸入。
- Q: 結案摘要寫入成功後的「離開動作」，是否要一併把平台上的對話狀態標記為已結束（resolved）？ → A: 不處理。寫入成功後直接 LEAVE（與 M2 的離開相同呼叫）。平台改對話狀態的能力已由 spike 28 實測過，但可改的狀態有多種、專案尚未討論到該層級，對話狀態變更整項延後另議。
- Q: 開啟結案面板時「歷來結案紀錄」查詢失敗、候選清單載不出來，系統應該怎麼做？ → A: 比照摘要產生失敗（FR-046）：顯示「無法載入結案紀錄」錯誤與重試按鈕，不產生草稿；客服可重試或取消結案。MUST NOT 靜默退回「從第一則起算」。
- Q: 「自訂起算時間」應只在對話從未被結案時提供，還是任何時候都可用？ → A: 任何時候都可用（與畫布 artboard 2b 一致）；它是候選只列最近 5 次時取得更早區間的唯一路徑。紀錄上的區間起點須可辨識為「自訂」而非結案時間點。

## 範圍界線

### 本規格交付

1. **結案摘要**：客服按下「結案」時產生，經人審後寫入 Data Board，寫入成功才離開對話
2. 摘要產生後先進**可編輯的人審面板**，客服確認並明確按下寫入後才寫進 Data Board
3. Data Board 的**冪等寫入**：重複觸發不得產生重複紀錄
4. Data Board **schema setup script**（可重跑、可驗證欄位齊全）
5. 「文案先於行為」這筆帳的結清，以及 003 SC-007 的重新驗證

> **「離開」＝純粹退出，不產生摘要、不寫入任何紀錄**（2026-09-03 拍板）。
> 兩個出口的差別因此是「有沒有產生摘要並寫入」，而不是「寫入哪一種摘要」。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 結案：AI 寫的摘要要先給人看過，才進得了 CRM (Priority: P1)

客服判斷這通對話已經處理完了，按下「結案」。系統先確認**這份報告要涵蓋哪一段**（預設已選好，
多數情況客服直接略過），再以**按下那一刻的對話快照**產生一份結案摘要草稿，在畫面上以**可編輯的面板**
呈現：摘要內容、意圖、分類、處理結果、實際採取的行動、情緒結果、引用過的 SOP、後續動作。
客服讀過、改過（模型寫錯的分類、漏掉的後續動作），確認無誤後**明確按下寫入**，
這份紀錄才進入 Data Board，並記下是誰、在什麼時間審過。寫入成功後才離開對話。

**Why this priority**: 這是整個規格的產品價值本體，也是憲法第五條的落點 ——
AI 產物寫進正式 CRM 之前必須有人看過。沒有這條，其餘各項都沒有存在的理由。
同時它是唯一能結清「文案先於行為」那筆帳的路徑。

**Independent Test**: 在一通有客戶發言的對話上 JOIN、按下結案、觀察是否出現可編輯的摘要面板、
改掉其中一個欄位、按下寫入、到 Data Board 上確認寫入的是**改過之後**的內容且帶有審核者與時間。
不依賴冪等行為即可驗證。

**Acceptance Scenarios**:

1. **Given** 客服已 JOIN 一通有客戶發言的對話，**When** 按下「結案」，**Then** 畫面出現可編輯的結案摘要面板，且此時 Data Board 上 MUST NOT 有任何新增或變更的紀錄。
2. **Given** 結案摘要面板已顯示草稿，**When** 客服修改其中任一欄位後按下寫入，**Then** Data Board 上的紀錄內容是**修改後**的版本，而非模型原始產出。
3. **Given** 結案摘要面板已顯示草稿，**When** 客服完全不操作、放置任意長的時間，**Then** 系統 MUST NOT 自動寫入（沒有操作就是沒有確認）。
4. **Given** 寫入成功，**When** 檢視該筆 Data Board 紀錄，**Then** 審核者與審核時間欄位有值，且對應到實際按下寫入的那位客服。
5. **Given** 客服正在結案面板中，**When** 客服重新整理頁面或登出，**Then** 等同**取消結案**：回到該對話時仍是 JOIN 狀態、面板照常展開、各區塊重新分析、不顯示結案摘要區塊、輸入框正常，且 Data Board 上沒有任何紀錄。
6. **Given** 客服正在結案面板中，**When** 對話抵達新訊息，**Then** 摘要**不**自動更新，畫面顯示「對話有新內容，建議重新產生」；客服按下「重新產生」時，以**當下**重新取一次快照。
7. **Given** 這通對話曾被結案過，**When** 按下「結案」，**Then** 畫面提供涵蓋區間的候選（既有結案時間點，降冪排列，「從第一則對話起算」墊底），每個候選標示則數，且預設已選中最上面則數大於 0 的那一個。
8. **Given** 摘要草稿已產生，**When** 客服改選另一個涵蓋區間，**Then** 摘要以新區間重新取快照並重新產生，MUST NOT 沿用舊區間的內容。
9. **Given** 寫入成功，**When** 檢視該筆紀錄，**Then** 實際涵蓋的區間起點與則數已一併寫入，且以該區間重算三個情緒數值會得到與紀錄相同的值。

### User Story 2 - 重複觸發不製造重複紀錄，也不銷毀服務歷史 (Priority: P2)

寫入 Data Board 時網路逾時了，客服不確定成功沒有，於是又按了一次。
系統 MUST 讓這兩次落在同一筆紀錄上。
但「同一通對話有多筆結案紀錄」是**正常的**，而且有兩種完全不同的成因：客戶結案後又回來問（不同時間的多次服務），
以及同一時段多位客服交叉服務、各自寫一份報告。這兩種都 MUST 並存，與「重按造成的重複」處置方式完全不同。

**Why this priority**: 這是 M3 驗收清單裡的獨立一項，且是憲法 5.3 的落點。
排在 P2 是因為它要在 US1 的寫入路徑存在之後才驗得了，但它**不是**可以延後的細節 ——
弄錯的兩個方向都很貴：一邊是報表出現重複紀錄，另一邊是服務歷史被靜默銷毀。

**Independent Test**: 對同一份草稿在寫入端故障注入逾時後重試 3 次，檢查 Data Board 上的筆數；
再以「兩次獨立結案」的情境檢查筆數。兩個情境的期望值不同，可各自獨立驗證。

**Acceptance Scenarios**:

1. **Given** 一份結案摘要草稿的寫入因逾時而結果未知，**When** 客服重試任意次數，**Then** Data Board 上與該份草稿對應的紀錄**恰好一筆**。
1a. **Given** 一份草稿的首次寫入逾時但實際已建立紀錄，**When** 客服修改草稿內容後重試，**Then** Data Board 上仍恰好一筆，且內容是**修改後**的版本（FR-030c）。
2. **Given** 客服按下「重新產生」取得一份新的草稿，**When** 寫入該新草稿，**Then** 正式紀錄上與該次結案對應的筆數仍為一筆 —— 被丟棄的舊草稿從未寫入，MUST NOT 出現「一次結案卻留下兩筆」。
3. **Given** 客服 B 已對同一通對話開啟結案面板、正在編輯草稿，此時客服 A 對該對話完成結案，**When** B 按下寫入，**Then** 兩筆紀錄**並存**、A 的紀錄內容不被更動，且 B 在按下寫入時 MUST 收到「A 已於 HH:MM 完成結案」的明確提示（FR-034），MUST NOT 讓第二筆靜默產生。
   （A 在 B 開啟面板**之前**就完成的結案，由 US1 情境 7 的候選清單那一列負責告知，寫入時不再重複提示 —— FR-034 於 2026-09-03 收窄的範圍。）
4. **Given** 同一通對話已有多筆結案紀錄，**When** 以對話識別碼查詢，**Then** MUST 能查出該對話歷來的全部結案紀錄，而非只有最後一筆。

### User Story 3 - 寫入失敗時，畫面 MUST NOT 顯示成功 (Priority: P2)

Data Board 寫入失敗（逾時、被拒、或平台回了成功但紀錄實際沒建立）時，
客服看到的 MUST 是失敗與可重試的提示，而且草稿 MUST 原封不動留在畫面上。
系統 MUST NOT 在未確認紀錄真的存在的情況下，關閉面板、離開對話、或顯示任何成功訊息。

**Why this priority**: M2 收尾時的三個靜默失效缺陷，全部是在各 spec 驗收「全數通過」之後才被找出來的
—— 它們不報錯、不觸發型別錯誤、且都落在既有自動化測試的盲區。
「寫入 Board 失敗但畫面顯示成功」是本規格裡形狀完全相同的一條路徑，因此**它必須是一條被明文驗收的
使用者故事，而不是 US1 的一個 edge case**。放進 edge case 清單就等於交給實作者自行判斷要不要測。

**Independent Test**: 以故障注入涵蓋四種失敗形態（逾時、4xx、5xx、回應成功但後續查不到該筆紀錄），
每一種都檢查畫面訊息與草稿是否還在。完全不需要真實 AI 產出即可驗證（草稿可為固定值）。

**Acceptance Scenarios**:

1. **Given** 客服在結案面板按下寫入，**When** 寫入請求逾時，**Then** 畫面顯示失敗與可重試提示、草稿仍在、面板不關閉、對話 MUST NOT 被離開。
2. **Given** 寫入請求收到平台的錯誤回應（4xx／5xx），**When** 畫面更新，**Then** 顯示的是失敗，且錯誤訊息 MUST NOT 洩漏任何憑證。
3. **Given** 寫入請求收到成功回應，**When** 系統回查該筆紀錄卻不存在，**Then** 該次 MUST 被當作失敗處置，MUST NOT 因為「回應是 200」就顯示成功。⚠️ 此情境的**呈現與其餘三種不同**（畫布 B8「寫入結果無法確認」vs B7「寫入 CRM 失敗」）：MUST 明說「請勿當成已完成」並給查驗步驟，主鈕為「已確認沒有，重試寫入」。兩者的**狀態機出口相同**（草稿保留、面板不關、不離開對話），只有文案與按鈕不同。
4. **Given** 摘要已確認寫入成功，**When** 後續的離開動作失敗，**Then** 結案 MUST 視為成功（不回退、不讓已寫入的紀錄變成孤兒），畫面 MUST 另外顯示一條可重試的離開失敗提示並說明「紀錄已寫入」。

### User Story 4 - 環境可重建：Data Board schema 由 script 建立並驗證 (Priority: P3)

換一套環境（新的測試組織、正式環境初次上線）時，負責佈署的人執行一支 setup script，
Data Board 與其全部欄位就建立完成；重複執行不會產生重複欄位。
script 同時能**驗證**現有 Board 的欄位是否與結案摘要的欄位逐欄對得上，缺哪一欄要講出來。

**Why this priority**: 前四個故事都以「Board 存在且欄位齊全」為前提，因此它是使能項而非產品價值。
排 P3 是因為可以先用手動建立的 Board 讓 US1～US3 跑起來。
但**驗證能力不可省**：`ARCHITECTURE.md` §13.3 已明載「少建一欄不會報錯，只會讓該維度在報表裡永遠是空的」
—— 這正是本規格最在意的那種靜默失效。

**Independent Test**: 在一個沒有該 Board 的環境執行 script，檢查 Board 與欄位；
再執行第二次，檢查欄位沒有變成兩份；手動刪掉一個欄位後執行驗證模式，檢查它有沒有被指出來。

**Acceptance Scenarios**:

1. **Given** 環境中尚無結案摘要 Board，**When** 執行 setup script，**Then** Board 與其全部欄位建立完成。
2. **Given** Board 已存在且欄位齊全，**When** 再次執行 setup script，**Then** 不產生重複欄位、不變更既有資料。
3. **Given** Board 少了任一欄位，**When** 執行 script 的驗證模式，**Then** 明確列出缺少的欄位名稱，並以失敗結果表示不通過。

### Edge Cases

- **結案期間有新訊息抵達**：摘要 MUST NOT 自動更新（快照語意），只顯示「建議重新產生」的過期標記。⚠️ 這與輸入框上方的常駐橫幅是**兩件事**：橫幅整段結案期間都在（說明快照規則），過期標記只在真的有新訊息時出現。
- **結案期間客服要回覆客戶**：輸入框**不鎖**，改以橫幅告知「結案中 —— 摘要內容為按下結案當下的對話快照，不含此後的新訊息。送出新訊息後，可按「重新產生」把它納入摘要。」（畫布逐字）。⚠️ 該尾句原為「要送出訊息請先取消結案。」，與同狀態下可用的輸入框矛盾（正是 SC-008 在數的落差）；**Design 已於 2026-09-04 修正畫布**，實作與畫布因此一致，**不是刻意偏離**。⚠️ 服務模式則**鎖住唯讀並附提示**（兩者的差別已於 2026-08-28 拍板：憲法 3.1／3.3 保護的是「還能看對話、還能回覆」，服務模式是設定項，不在保護標的內）。
- **客服按下結案後切去處理別的對話、忘了回來**：左側對話清單標記「有未完成的結案」。MUST NOT 做成倒數計時或閒置自動寫入。該標記與結案狀態同生共死，重新整理後一併消失。
- **兩個人同時對同一對話結案**：**不阻擋**（曾經 JOIN 過的人都有資格結案，兩份摘要內容本來就可能不同），presence 顯示「XXX 正在結案」作為提示。
- **同一次服務中，同事剛結案而我也要結案**：候選清單最上面那個 `closedAt` 距今只有幾分鐘、對應 **0 則**。此時預設 MUST 跳到下一個（則數 > 0 的），而 0 則的候選仍要看得出來（FR-021c／FR-021d）。
- **長期客戶按下「從第一則對話起算」**：可能是數百則、橫跨半年。選項上的則數就是唯一的煞車，MUST 顯示（FR-021c）。
- **區間內評分點不齊（跨小時的服務、或冷啟動 50 則沒涵蓋到起點）**：三個情緒數值 MUST 留空並標示實際涵蓋範圍，MUST NOT 以區間內現有點的最低值頂替 —— 那會安靜地把「近期最低點」寫成「本次最低點」，而且要到寫進 Data Board 之後才會被發現（FR-022b）。
- **模型產出的受控詞彙不在白名單內**：分類／處理結果／實際行動等統計用欄位的值不在設定檔中時，該欄位 MUST 留空並要求客服自行選擇，MUST NOT 直接寫入模型自由生成的值（憲法 4.6）。
- **摘要產生本身失敗**：面板顯示錯誤與重試按鈕，MUST NOT 呈現一份空白草稿讓客服誤以為「這通對話沒什麼可寫的」。
- **候選清單載入失敗（歷來結案紀錄查不到）**：面板顯示「無法載入結案紀錄」與重試按鈕，**不產生草稿**，客服可重試或取消結案。MUST NOT 靜默退回「從第一則起算」—— 那會讓長期客戶的報告安靜地涵蓋整個聊天室歷史，且沒有任何提示（FR-021h）。
- **未曾 JOIN 過的人按下結案**：不在本規格新增權限判斷；沿用既有的 JOIN 判定，兩個出口按鈕的可見性條件不變。

## Requirements *(mandatory)*

### 兩個出口的行為（結清「文案先於行為」）

- **FR-001**: 系統 MUST 讓「離開對話」與「結案」是**兩條各自完整的行為路徑**：前者僅退出、不寫入任何正式紀錄；後者進入結案流程，產生摘要供客服編輯確認後寫入正式紀錄。
- **FR-002**: 本規格落地時 MUST 回頭確認 `conversation.exitHint` 這行文案與**實際行為**已經一致；若有任何殘餘落差，MUST 在本規格內修正其中一方，MUST NOT 留下第二筆「文案先於行為」的帳。
- **FR-003**: `specs/003-analysis-trigger-policy` 的 SC-007 MUST 在本規格內**重新驗證**（而非再次結案）；驗證方式見 SC-005。
- **FR-004**: 「結案」MUST 維持 003 FR-022a 的獨立行為路徑，MUST NOT 被改寫成「離開對話」的別名或其某個參數值。
- **FR-005**: 結案流程進行中時，該對話的分析 MUST 照常執行；分析門檻 MUST 維持 003 FR-012 的單一條件「該對話目前是否仍有人 JOIN」，MUST NOT 為結案流程新增第二個條件。⚠️ M2 現況「結案即停止分析」是**階段性行為**，本規格改掉它 MUST NOT 被當成 regression。

### 人審面板（憲法第五條）

- **FR-010**: 結案摘要在寫入正式紀錄之前，MUST 先以**可編輯**的形式呈現給客服。
- **FR-010a**: 面板欄位 MUST 分為兩類。**唯讀**：涵蓋區間起點與則數、`sentimentStart`／`sentimentEnd`／`sentimentTrough`、審核者與審核時間、參與客服（`operators`）、`joinedAt`／`closedAt` —— 這些是系統由事實計算或於寫入時記錄的欄位，客服 MUST NOT 能手動改寫（否則 SC-006b 的重算驗證失去意義）。**可編輯**：摘要、意圖、分類、處理結果、實際採取的行動、情緒結果標籤、引用的 SOP、後續動作。其中分類、處理結果、實際採取的行動、情緒結果標籤 MUST 以設定檔白名單的選擇呈現，MUST NOT 提供自由輸入（FR-015、憲法 4.6）。
- **FR-011**: 系統 MUST 只在客服**明確按下寫入動作**時才寫入正式紀錄。MUST NOT 因為客服按下離開／結案、因為摘要產生完成、或因為閒置逾時而自動寫入。
- **FR-012**: 寫入的內容 MUST 是客服**編輯後**的版本，MUST NOT 是模型的原始產出。
- **FR-013**: 每一筆寫入的紀錄 MUST 記錄審核者與審核時間，使其事後可稽核。
- **FR-014**: 若日後確有自動寫入的需求，該筆紀錄 MUST 標記為未經人審（審核者欄位留空），使其可於事後被稽核篩出。**本規格不交付任何自動寫入路徑。**
- **FR-015**: 統計用的受控詞彙欄位（分類、處理結果、實際採取的行動）MUST 取自設定檔，MUST NOT 由模型自由生成（憲法 4.6）。設定檔 MUST 隨本規格建立。

### 只有一種摘要

- **FR-016**: 本規格 MUST 只產生**一種**摘要：**結案摘要**（觸發：**只有**客服按下「結案」；平台側對話狀態的變化在本規格**不是**觸發條件，見「明確排除」；讀者：報表與稽核；內容：完整的意圖／分類／處理結果／情緒起訖／後續動作）。
- **FR-016a**: 「離開對話」MUST NOT 產生任何摘要、MUST NOT 寫入任何正式紀錄，行為維持 M2 現況（退出 ＋ 停止分析 ＋ 隱藏面板）。⚠️ 這代表 `HandoverSummary` 在本規格**不實作**，理由與改判義務見「範圍界線」與「本規格造成的文件改判義務」。
- **FR-017**: 因為只有一種摘要，`ARCHITECTURE.md` §18 M3 的「兩者不混用」在本規格 MUST 記為**不適用**，MUST NOT 打勾 —— 只有一種摘要時該條自動成立卻什麼都沒驗到，打勾會讓下一個人以為它驗過了。
- **FR-019**: 「手動結案」不限於獨立的結案按鈕 —— 若設計成離開流程中「同時結束對話」的選項，只要目的是結束本次服務並留下結案紀錄，就 MUST 走同一條結案路徑與同一份結案摘要形狀。

### 摘要內容的事實來源

- **FR-020**: 送去產生摘要的對話內容 MUST 是**按下結案那一刻的快照**。之後抵達的訊息 MUST NOT 進入摘要，除非客服按「重新產生」（＝以當下重新取一次快照）。⚠️ 實作時很自然會寫成「送出時取最新」，那會讓客服確認過的內容與實際寫入的內容不一致。
- **FR-020a**: 任一摘要欄位在事實來源不足時 MUST 留空並於面板上標示原因，MUST NOT 以近似值或模型推測值頂替（憲法「事實不得推測」）。「標示原因」依欄位類型界定：三個情緒數值以 `sentimentNote` 說明實際涵蓋範圍（FR-022b）；受控詞彙欄位以「請選擇」提示表示「模型產出不在白名單內」（FR-015）；其餘自由文字欄位（摘要、意圖、後續動作）留空即可，不另標原因 —— 摘要或意圖為空時整份視為產生失敗（FR-046），不會以空白草稿呈現。

### 本次結案的涵蓋區間

> **問題**：一個對話（例如 LINE@ 的一位客戶）是**長期存在**的，可能被服務過很多次
> —— 六個月前 20 則、三個月前 50 則、昨天 25 則、今天 25 則。
> 這次結案報告要涵蓋哪一段？切錯不會報錯，只會讓摘要、意圖與三個情緒數值全部指向錯的區間。

- **FR-021**: 每一份結案摘要 MUST 明確界定其**涵蓋區間**（起點訊息 → 終點快照），且該區間 MUST 只由「對話本身的事件」決定：
  - MUST NOT 由**客服自己的 JOIN 時間**推導 —— 同一次服務的多位客服 JOIN 時間不同，會產出不同區間；且客戶通常在客服 JOIN 前就已把訴求講完，從 JOIN 起算會漏掉意圖。
  - MUST NOT 由**時間間隔（gap）規則**推測 —— 客戶下午發言、隔天早上才有客服接手是常態（例：昨天 17:35 客戶送出、今天 10:15 客服 A 進入、10:25 客服 B 接手，空檔 16 小時 40 分，卻是同一個區間）。任何固定的間隔門檻都會在這類情況切錯，而門檻值無法從證據推導，只能猜。
  - MUST NOT 由「客戶那一輪發言的第一則」推導 —— 客服回過話但**沒有結案**時，客戶隔天追問仍屬同一輪，此規則會誤切成新一輪。

- **FR-021a**: 起點 MUST 由客服在人審面板上從一組候選中選定。候選 MUST 為：該對話最近 **5 筆結案紀錄的 `closedAt`**（每一筆代表「上一輪服務在此結束」），加上固定墊底的**「從第一則對話起算」**安全網選項。選定某個 `closedAt` 後，起點為該時間點之後的第一則訊息。
  > **為什麼用 `closedAt` 而不是時間間隔**：「有沒有結案」本身就是「上一輪有沒有結束」的定義，是**事實**而非推測。客服回過話且已結案 → 客戶隔天追問是新一輪；回過話但未結案 → 隔天追問仍是同一輪。這個區別只有 `closedAt` 分得出來。
  > **為什麼 5 筆夠**：同一時段同時服務的客服（含中途接手的高層）不太可能超過 5 位，往回數 5 個 `closedAt` 必然會碰到上一輪的結束點。真的超過也不會卡死 —— 安全網選項最壞是涵蓋過多，不會漏掉。

- **FR-021b**: 候選 MUST 以**時間降冪**排列（距今最近的 `closedAt` 在最上，越早越往下），「從第一則對話起算」MUST 固定排在**最後一個**，避免被誤按。
- **FR-021c**: 每個候選 MUST 標示其對應的**訊息則數**（例如「9/2 14:30 起 · 25 則」／「從第一則對話起算 · 398 則」）。⚠️ 這是客服在選之前唯一能判斷份量的依據，MUST NOT 只顯示時間。
- **FR-021d**: 預設 MUST 選中「最上面**則數大於 0**」的候選。⚠️ MUST NOT 單純預設最上面那一個 —— 同一次服務中同事剛結案時，最近的 `closedAt` 距今只有幾分鐘，對應則數為 **0**，那是個荒謬的預設值。
- **FR-021e**: 該對話從未被結案過時（無任何候選），MUST 明白告知客服「這則對話從未被結案，預設從第一則起算」。
- **FR-021e-1**: 「自訂起算時間」MUST 在**任何時候**都可用，不限於從未結案的狀態 —— 候選只列最近 5 筆 `closedAt`，更早的區間只能靠它取得。客服自行輸入日期時分後，起點為該時點之後的第一則訊息，並比照 FR-021g 重新取快照與重新產生。自訂起點 MUST 在面板與正式紀錄上皆可辨識為「自訂起算時間（非結案起點）」，MUST NOT 被當成真實的結案事件呈現或記錄。
  > ⚠️ **與 FR-021c 的刻意偏離**：自訂起算時間在**套用前不提供則數預估**（畫布 2b 的「約 N 則」一行不實作 —— 需要額外一次訊息掃描），套用後才以涵蓋說明那一行（FR-021f）呈現實際則數。FR-021c 的「則數是唯一的煞車」在這條路徑上因此是**事後**的煞車：客服看到則數過大時可再改選或取消。已記入 `docs/DESIGN_FEEDBACK.md` D-5 請 Design 確認。
- **FR-021f**: 實際涵蓋的**區間與則數** MUST 一併寫入正式紀錄，並在面板上以一行唯讀說明呈現。⚠️ 選錯區間本身不會有任何錯誤提示 —— 這行說明與紀錄上的區間欄位，是事後唯一能看出「這份報告到底涵蓋了什麼」的依據，也是報表能否比較同類資料的前提。
- **FR-021g**: 客服變更涵蓋區間後，摘要 MUST 以新區間重新取快照並重新產生，MUST NOT 沿用舊區間產生的內容。
- **FR-021h**: 候選清單所依賴的「該對話歷來結案紀錄」查詢失敗時，面板 MUST 顯示錯誤與重試按鈕，MUST NOT 產生草稿、MUST NOT 以任何預設區間（含「從第一則對話起算」）頂替；客服 MUST 仍可取消結案。處置方式與 FR-046 一致：未能確定區間就沒有摘要。

### 情緒數值的範圍

- **FR-022**: `sentimentStart`／`sentimentEnd`／`sentimentTrough` MUST 全部以 FR-021 的涵蓋區間計算，三者 MUST 同範圍。⚠️ 若三者範圍不一致（例如頭尾取本次、最低點取整個聊天室的歷史），同一筆紀錄裡的三個數值會來自不同時間段，報表直接失去意義。
- **FR-022a**: `sentimentTrough` 是**該區間內**的最低點。MUST NOT 取 sparkline 繪出的最近 N 點（那會算成「近期最低點」），也 MUST NOT 跨越區間邊界取到前幾輪服務的谷底。
- **FR-022b**: 區間內的評分點不齊全時（2 小時滑動 TTL 已過期，或冷啟動的 50 則上限未涵蓋到區間起點），三個情緒數值 MUST 留空並標示實際涵蓋範圍，MUST NOT 以區間內現有點的最低值頂替。「留空」與「0 分」在紀錄上 MUST 可區分 —— 否則報表會把留空當成最低分。
  > 日後若拍板將評分點持久化（`CONSTITUTION.md` 5.3 同批待拍板），這些欄位會自然開始有值，報表與介面都不必改動。

### 寫入與冪等

- **FR-030**: 冪等的單位 MUST 是**摘要草稿**，不是對話，也不是「對話 ＋ 客服」。同一份草稿無論被寫入幾次，MUST 恰好對應一筆正式紀錄（寫入逾時後客服重按 MUST NOT 產生第二筆）；除此之外的每一次結案 MUST **各自產生獨立的紀錄並存**，MUST NOT 互相覆蓋。

  ⚠️ **同一通對話會有多筆結案紀錄，有兩個性質完全不同的原因，兩者 MUST 都被支援**：

  | # | 情境 | 例 |
  |---|---|---|
  | ① **不同時間的多次服務** | 同一個聊天室（例如 LINE@ 的同一位客戶）在不同時期被服務多次 | 六個月前 20 則、三個月前 50 則、昨天 25 則、今天 25 則 —— 四次獨立的服務 |
  | ② **同一次服務、多位客服各自結案** | 同一個時間段內多位客服 JOIN、交叉服務或中途轉手，兩人都有資格對**同一個對話區間**做結案報告，且兩份內容本來就可能不同 | A 與 B 同時段服務，各送一份 |

  覆蓋在①會銷毀服務歷史、讓報表把多次服務算成一次；在②會讓後送出的那份把先送的洗掉，而那是另一位同事的工作成果。
- **FR-030a**: 正式紀錄的主鍵 MUST 是獨立識別碼，對話識別碼 MUST 降為**可重複的索引欄位**（供「查出這通對話歷來的所有結案紀錄」）。
- **FR-030b**: 上述兩條依賴 `CONSTITUTION.md` 5.3 的 MAJOR 修憲。✅ **已於 2026-09-03 完成，發布為 v4.0.0** —— 條文改寫、`ARCHITECTURE.md` 八處落點、`IMBRACE_QUESTIONS.md` D-2、`specs/003` 的提案節點、附錄 C 版本紀錄與 `.specify/memory/constitution.md` 同步皆已完成。本規格的開工前提因此解除。
- **FR-030c**: 同一份草稿的重試寫入 MUST 以草稿 id 找到既有紀錄後**更新為當下的草稿內容**（查無則建立、查有則更新）。客服在逾時後修改草稿再重試時，正式紀錄的內容 MUST 等於客服**最後一次確認**的版本，MUST NOT 停留在首次（結果未知的）寫入所送出的內容 —— 否則畫面上確認的與 Board 上存的會不一致，且不會有任何錯誤提示。審核時間以最後一次成功寫入為準。
- **FR-031**: 系統 MUST 在寫入後**確認該筆紀錄確實存在**才視為成功。收到成功回應但回查不到該筆紀錄時，MUST 當作失敗處置。
- **FR-032**: 寫入失敗時，系統 MUST 顯示失敗與可重試提示、MUST 保留草稿內容、MUST NOT 關閉面板、MUST NOT 離開對話、MUST NOT 顯示任何成功訊息。
- **FR-032a**: 寫入路徑（查詢 → 建立／更新 → 回查）MUST 有**硬逾時上界**，逾時即依 FR-032 轉為失敗處置。⚠️ **這是 FR-040a「寫入中不可取消」的成立前提** —— 兩者缺一，客服就會被困在一個既不能取消、也不會自己結束的狀態裡。
  > 逾時值取 **30 秒**（沿用 `KNOWLEDGE_SEARCH_TIMEOUT_MS` 的既有量級）。依據：寫入是三次 Board API 呼叫，實測單次為次秒級（`scripts/spike/out/29-*.json`），30 秒已是極寬鬆的上界。
  > ⚠️ 這個門檻 **MUST NOT 被 SC-004 的「不設固定秒數門檻」波及** —— 那條講的是**摘要產生**（工作量隨涵蓋區間變動，訂任何秒數都是錯的口徑）；寫入的工作量固定為三次呼叫，正是應該有門檻的那一類。
- **FR-032b**: 客服在寫入中強制離開（重新整理、關閉分頁）時，MUST 不造成資料損害：該次寫入可能已在平台端完成，此時 Board 上留下的是**客服已確認過的正確紀錄**，帶有審核者與審核時間。⚠️ 風險不是資料錯誤，而是**客服不知道它成功了**而重做一次結案 —— 那會產生第二個 `draftId`、第二筆紀錄（FR-030 允許並存，因此不會被冪等擋下）。緩解由既有機制承擔：下次開啟結案面板時，該筆會出現在涵蓋區間的候選清單最上方且對應 **0 則**（FR-021d／畫布 `zeroTop` 狀態），客服看得見。**本規格不為此新增任何機制。**
- **FR-032c**: 寫入失敗的**呈現**MUST 分兩種，依「客服接下來該做什麼」而非錯誤碼區分（畫布 B7／B8，逐字規格見 `DESIGN_TOKENS.md` §7.2）：
  - **B7『寫入 CRM 失敗』**（逾時、4xx、5xx）：可直接重試，附備援管道與次鈕「回報 IT」。
  - **B8『寫入結果無法確認』**（回應成功但回查不存在）：MUST 明說「請勿當成已完成」並給 CRM 查驗步驟；主鈕為「已確認沒有，重試寫入」，**無次鈕**。
  - ⚠️ 兩者的**狀態機出口 MUST 是同一個**（回 `ready`、草稿逐欄保留、面板不關、不離開對話）—— 分成兩條路徑維護「草稿還在不在」，漏掉一邊不會報錯。差異 MUST 只在文案與按鈕。
  - ⚠️ B8 的文案 **MUST NOT** 宣稱「重試可能產生重複紀錄」。實測（`spike:board-write` 006-E10，n=3）建立後 47～55ms 即可被 `q` 搜尋到、`getItem` 3/3 立即可取，重試會命中既有紀錄走更新。宣稱一個不存在的風險，與 FR-002 在修的「文案承諾與實際行為不符」是同一類問題。⚠️ 該量測條件為小型 board、低負載。
- **FR-035a**: 寫入端點 MUST 產生一個**請求識別碼**（`reqId`），於請求進入時產生、三步（搜尋／建立或更新／回查）各記一行日誌帶著它，並於成功與失敗的回應中一併回傳，供畫面的 meta 列顯示（畫布 `failMeta` 的 `req 8f2c-41`）。
  > ⚠️ **MUST 在請求進入時產生，MUST NOT 只在出錯時產生** —— 只有出錯才有 id 的話，看不到出錯**之前**發生什麼，而 B8 要判斷的正是「平台沒建」還是「我方回查用錯 id」，那需要前兩步的紀錄。
  > ⚠️ `reqId` MUST NOT 含任何憑證或對話內容（FR-035、憲法 1.5）；它與 `draftId`／`recordId` 同屬「只留 id 與雜湊」的形狀。
- **FR-033**: 寫入成功後的「離開動作」MUST 只是 LEAVE（與「離開對話」相同的退出呼叫），MUST NOT 變更平台上的對話狀態（見「明確排除」）。該離開動作失敗 MUST NOT 回退整個結案；MUST 顯示一條可重試的失敗提示，並讓客服看得出「紀錄已寫入、只是還沒離開」。
- **FR-034**: **在面板開啟之後才新出現**的他人結案，MUST 於按下寫入時明確提示（含對方與完成時間）。⚠️ 該提示的用途是**告知**而非阻擋 —— 依 FR-030 ②，同一次服務由多位客服各自結案是**正常情境**，提示 MUST NOT 被寫成警告或需要額外確認的攔截，也 MUST NOT 讓後一位以為自己會覆蓋掉對方。
  > ⚠️ **範圍已於 2026-09-03 收窄**：面板開啟當下就已存在的結案紀錄，客服在涵蓋區間的候選清單上**已經看過一次**（該列逐字為「林佩君已於 11:20 結案 · 此後尚無新訊息」）。寫入時再提示一次同一件事，只會讓客服學會忽略這類提示。本條要抓的是**我在編輯期間**同事才完成的那一筆 —— 那是客服無從得知的新資訊。
- **FR-035**: 任何寫入相關的錯誤訊息 MUST NOT 洩漏憑證或 API 金鑰。

### 結案流程的狀態與呈現

- **FR-040**: 結案流程的狀態 MUST 只活在該瀏覽器分頁內；重新整理或登出 MUST 等同**取消結案**，且因為此時尚未寫入任何紀錄，取消 MUST NOT 需要任何清理或補償動作。
- **FR-041**: 有未完成結案的對話 MUST 在左側對話清單上被標記；該標記 MUST 隨結案狀態一併消失，MUST NOT 做成倒數計時或閒置自動寫入。
- **FR-042**: 結案期間輸入框 MUST NOT 被鎖定；MUST 在其上方顯示常駐橫幅說明**快照規則**。⚠️ 該橫幅 MUST NOT 出現「要送出訊息請先取消結案」這類暗示輸入框被鎖的措辭（見上方 Edge Cases）。取消結案的控制項在**中欄標題列**，不在橫幅裡（FR-040a）。
- **FR-043**: 結案期間服務模式 MUST 為唯讀並附提示。
- **FR-044**: 結案期間有新訊息抵達時，MUST 在摘要區塊顯示「對話有新內容，建議重新產生」的過期標記；該標記 MUST 與 FR-042 的常駐橫幅是兩個獨立的呈現。
- **FR-045**: 系統 MUST NOT 阻擋兩位客服同時對同一對話結案；SHOULD 於 presence 呈現「XXX 正在結案」。⚠️ 該訊號 MUST 是不持久化的即時提示，MUST NOT 因此讓 FR-040 的「結案狀態只活在分頁內」失效。
- **FR-046**: 摘要產生失敗時 MUST 顯示錯誤與重試按鈕，MUST NOT 呈現空白草稿。
- **FR-046a**: 摘要產生期間的等待呈現 MUST 誠實（SC-004）：
  - MUST NOT 顯示任何**會過期的時間承諾**（「約 N 秒完成」「最長 N 秒」）。耗時由涵蓋區間長度決定，任何固定值都會在長對話上失準。MUST 改用不含時間承諾的措辭，並說明**長對話需要較久**。
  - **首次產生中沿用畫布既有的忙碌態呈現**（`scopeRegen`／`writing` 是同一種樣式：按鈕收成單一忙碌鍵 ＋ 旋轉 icon），只換文案 —— 用**產生**的語意而非「寫入中…」，且不帶秒數。不另外向 Design 要一個新狀態。
  - MUST NOT 在完成前呈現任何「已完成」的訊號。
  - 產生期間 MUST 可取消結案（見 FR-040a）。
- **FR-040a**: 結案流程 MUST 提供明確的**取消**控制項，且在**寫入中（已送出寫入請求、結果未知）以外的任何狀態**都可用 —— 包含候選查詢中、摘要產生中、以及各種錯誤狀態。
  - **寫入中 MUST NOT 可取消**：請求已送出而結果未知，此時取消會讓畫面當作沒發生過，但 Board 上可能已有紀錄 —— 那正是 US3 在防的孤兒。寫入中一律等它落定（成功或失敗），再由客服決定下一步。
  - ⚠️ **這條成立的前提是 FR-032a 的硬逾時**：沒有上界的話，「不可取消」等於「被卡住出不來」。兩條 MUST 一起讀 —— **摘要產生不設時間上限但隨時可取消；寫入有時間上限但期間不可取消**。兩者只要拿掉一半，客服就會被困在某個狀態裡。
  - 取消 MUST NOT 需要任何清理或補償動作（FR-040）。
  - **控制項的落點照畫布**：中欄標題列的「結案」在結案期間換成「**取消結案**」＋「結案中…」，並附輔助說明「取消結案＝回到已接手狀態，不會留下任何紀錄」（`DESIGN_TOKENS.md` §0 的 1c「結案中」狀態）。第 6 區塊維持畫布的兩顆按鈕（重新產生／一鍵寫入 CRM），**MUST NOT** 在區塊內另開第三顆取消鍵。
  - ⚠️ **寫入中時，標題列的那顆「取消結案」MUST 一併鎖住** —— 畫布只定義了第 6 區塊兩顆按鈕在該狀態的鎖定，標題列那顆沒有定義。已列入 `docs/DESIGN_FEEDBACK.md` D-4 請 Design 確認。
- **FR-047**: 結案摘要區塊在**未進入結案流程時 MUST 完全不呈現** —— 不是收合、不是變灰、不是骨架，是整塊不存在（`ARCHITECTURE.md` §14.1.1）。兩個理由：① 常駐會讓該區塊與「結案」按鈕的關係曖昧不明；② 區塊若常駐就得在某個時機產生內容，等於每個對話都多跑一次 AI 呼叫，而絕大多數對話不會在那一刻結案。
- **FR-047a**: 進入結案流程時，該區塊 MUST **移到面板最上方**並展開可編輯，其餘區塊 MUST 全部收合成單行。⚠️ 既然它平時完全不呈現，出現時對客服就是一個憑空冒出來的新元素 —— 置頂才不會讓人在面板中間找它（2026-09-03 使用者裁示）。
- **FR-047b**: 結案完成（寫入成功）或取消結案後，該區塊 MUST 再度消失。⚠️ 包含「摘要已寫入但離開失敗」那個狀態 —— 結案本身已完成，區塊 MUST NOT 留在畫面上。

### 環境與 schema

- **FR-050**: 系統 MUST 提供一支可重複執行的 setup script，用以建立結案摘要 Board 與其全部欄位；重複執行 MUST NOT 產生重複欄位或變更既有資料。
- **FR-051**: 該 script MUST 具備**驗證模式**：比對現有 Board 的欄位與結案摘要的欄位是否逐欄對得上，缺漏 MUST 被明確列出並以失敗結果回報。
- **FR-052**: 正式紀錄的欄位 MUST 與結案摘要的欄位逐欄對應；新增或改名任一欄位時 MUST 同步更新 script 與其驗證清單。

### Key Entities

- **涵蓋區間**：這一份結案報告所描述的那一段服務，由「起點訊息 → 終點快照」界定。起點由客服從既有結案紀錄的 `closedAt` 中選定，因為「有沒有結案」是唯一能分辨「上一輪結束了沒有」的事實。它決定摘要讀哪些訊息、三個情緒數值算哪一段，**因此 MUST 隨紀錄一起寫入**，否則事後無從得知這份報告涵蓋了什麼。
- **結案摘要草稿**：按下結案那一刻產生、只活在瀏覽器分頁內的可編輯內容。它是人審的標的，也是冪等寫入的單位 —— **一份草稿至多對應一筆正式紀錄**，按「重新產生」則產生新的一份。
- **正式結案紀錄**：寫入 Data Board 的業務資產，供查詢與製作報表。除摘要內容外必帶審核者與審核時間。
- **受控詞彙設定檔**：分類、處理結果、實際採取的行動等統計用欄位的合法值來源。它的存在理由是「報表要能統計」，因此模型 MUST 從中選擇而非自由生成。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 寫入正式紀錄的結案摘要中，**100%** 可回推到某位客服在面板上明確按下寫入的動作與時間；自動寫入筆數為 **0**。
- **SC-002**: 同一份草稿在寫入端故障注入下重試 **10** 次後，正式紀錄上與該草稿對應的筆數恰好為 **1**。
- **SC-003**: 四種寫入失敗形態（逾時、4xx、5xx、回應成功但回查不存在）各注入 **10** 次，畫面顯示成功的次數為 **0**，草稿遺失的次數為 **0**。
- **SC-004**: 結案摘要的產生**不設固定秒數門檻**；改以「**畫面在等待期間 100% 誠實**」驗收：任意 **20** 次產生（涵蓋短、中、長三種區間）中，畫面顯示「已完成」而實際尚未完成的次數為 **0**、顯示一個會過期的時間承諾（如「約 N 秒完成」）的次數為 **0**、產生期間無法取消結案的次數為 **0**。

  > ⚠️ **2026-09-03 修訂：原文為「90 百分位 ≤ 10 秒（沿用既有的摘要時效門檻）」，該門檻已撤銷。**
  > 撤銷的理由**不是**「我們達不到」（原文正確地禁止了那種放寬），而是**口徑本身套錯了**：
  > 那 10 秒是為**增量摘要**訂的 —— 每次只看新增的幾則訊息，工作量固定。
  > 結案摘要看的是**整段服務**，可能數百則（實測單一對話最多 398 則），
  > 工作量由涵蓋區間長度決定。拿固定工作量的門檻去量變動工作量的作業，
  > 訂多少都是錯的：訂緊了長區間永遠紅，訂鬆了短區間永遠綠，兩種都量不到真正的東西。
  >
  > 實測參考值（`spike:closure-agent`，n=8，9 則訊息的短區間）：中位數 9.4 秒。
  > 長區間預期顯著更久，**逾 1 分鐘為可接受**（2026-09-03 使用者裁示）。
  > 這個數字只作為容量規劃參考，**MUST NOT 回頭變成驗收門檻**。
  >
  > ⚠️ 因此真正要防的風險改變了：不再是「太慢」，而是「**慢的時候騙人**」——
  > 顯示一個過期的時間承諾、把未完成畫成完成、或讓客服在等待期間卡住無法脫身。
  > 三者都由本條驗收，且都對應 FR-046a。
- **SC-005**: 找 **3 位未參與本專案**的人，在按下之前正確說出「離開對話」與「結案」的差別（會不會留下紀錄），**3/3 通過**。以介面文案本身可讀出為準，不依賴教育訓練。（＝重跑 003 SC-007）
- **SC-006**: 「離開對話」在 **20** 次觸發中，產生摘要的次數為 **0**、寫入正式紀錄的次數為 **0**，且 003 SC-002（離開後 5 秒內不再產生新分析）維持 **20/20** 通過。
- **SC-006a**: 涵蓋區間的四個代表情境各測 **5** 次，選出的區間正確率 **100%**：① 同一聊天室的第 N 次服務（不含前幾輪）；② 同事五分鐘前剛結案、我也要結案（與同事同區間，非 0 則）；③ 客戶昨天 17:35 發言、今天 10:15 才有人接（同一區間，不因跨天被切開）；④ 該對話從未被結案過（從第一則起算，並告知客服）。
- **SC-006b**: 寫入正式紀錄的每一筆，**100%** 帶有實際涵蓋區間與則數；以該欄位重算三個情緒數值，與紀錄上的值一致的比率為 **100%**（不一致代表區間與數值來自不同範圍）。
- **SC-007**: 在一個全新環境執行 setup script 兩次後，Board 欄位與結案摘要欄位**逐欄對得上**且無重複欄位；手動移除任一欄位後，驗證模式 **100%** 指出缺漏。
- **SC-008**: 本規格交付後，介面文案所承諾的兩個出口行為與實際行為的落差項目數為 **0**（逐條對照 `conversation.exitHint` 的每個分句）。

## Assumptions

- **本規格不變更平台上的對話狀態**：結案＝寫入正式紀錄 ＋ LEAVE，對話在平台上的狀態維持原樣；「標記 resolved」延後另議（見「明確排除」）。本規格不新增對外契約。
- **人審面板沿用右欄既有的區塊結構**：`ARCHITECTURE.md` §14.1.1 已把「結案摘要自動填入」列為右欄第六區塊，本規格填入它而非另開一個容器。
- **結案期間的分析結果客服看不到是可接受的**：區塊已收合，但那些結果在取消結案後立即可用（2026-08-28 拍板）。
- **不新增權限模型**：誰能結案沿用既有的 JOIN 判定，不引入角色概念（憲法 7.6）。
- **429 沿用現況**：本規格期間 429 直接轉錯誤狀態供手動重試，全域退避佇列不在範圍內。
- **平台的 Board 欄位不保證支援唯一性約束**：實測（`scripts/spike/out/09-board-field-types.json`）在 5 個 Board 上未觀察到任何唯一鍵欄位型別，因此冪等 MUST 由寫入前的查詢與寫入後的回查共同保證，MUST NOT 假設平台會擋掉重複。

## 驗收方式的補充要求（M2 的教訓）

M2 收尾時修掉的三個靜默失效缺陷，**全部是在各 spec 驗收「全數通過」之後**、於**跨 spec 的交會處**
才被找出來的：它們不報錯、無型別錯誤，且都落在既有自動化測試的盲區。

因此本規格的驗收 MUST 額外滿足：

1. **US3 是獨立的使用者故事而非 edge case** —— 「寫入 Board 失敗但畫面顯示成功」這條路徑
   有自己的驗收場景與量化指標（SC-003），不倚賴實作者自行判斷要不要測。
2. **綠燈基線之外，MUST 另審一次跨 spec 的熱點檔案** —— 本規格會動到 003 已定案的結案出口
   與分析門檻，那正是「後面的 spec 動到前面 spec 的程式碼」的形狀。
3. **每一條「不報錯但會做錯事」的路徑 MUST 有一個會紅的迴歸測試**，至少涵蓋：
   寫入回應成功但紀錄不存在、快照被實作成「送出時取最新」、
   全程情緒最低點被算成近期最低點、Board 少建一欄導致該維度在報表裡永遠是空的。
